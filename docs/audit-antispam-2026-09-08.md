# Аудит: спамблоки и заморозки аккаунтов — рассылка и автоподписка

Дата: 2026-09-08. Ветка: `arena/01a0803f-tg-forward-pro`.
Проверены: `app/telegram_client/jobs.py`, `manager.py`, `forwarder.py`, `queue.py`,
`filters.py`, `app/webapp_api.py` (create/update task, COMMANDS), `webapp/app.js` (формы),
`app/config.py`, `app/db/repo.py`, `tests/test_antiban.py`, `tests/test_mailing.py`.

## Короткий вывод

Код аккуратно соблюдает `FloodWait` и считает дневные лимиты, но **не распознаёт
главный сигнал спамблока — `PeerFloodError`**, и продолжает отправлять/вступать/инвайтить
после него. Временная метка превращается в полноценный спамблок и заморозку именно так:
ограничение → код долбит дальше → Telegram ужесточает.

Вторая половина проблемы — **дефолтный темп**: рассылка 5 сек между чатами / 10 сек между
кругами, автоподписка 2 сек между вступлениями без дневного лимита. Это темп спам-бота,
а не человека. Плюс все аккаунты сервиса ходят под одним `api_id`, с одного IP и с
одинаковым отпечатком устройства — Telegram связывает их в одну сеть и мёрзнут они пачкой.

То есть жалобы пользователей объясняются кодом, а не «злым Telegram». Ниже — находки
по степени тяжести, с точными местами и что делать.

---

## P0 — критично: прямые причины спамблоков

### 1. `PeerFloodError` нигде не обрабатывается
**Где:** весь движок. `grep PeerFlood app/` — ноль совпадений в `jobs.py` / `manager.py` /
`forwarder.py` / `queue.py`.

**Что происходит сейчас:**
- Рассылка (`manager._mailing_tick` → `_mailing_failed`, manager.py:1589/1753): `PeerFlood`
  падает в generic `except Exception` → пауза **30 секунд** → повтор в тот же чат → снова
  `PeerFlood` → и так по кругу. В `is_hopeless_chat_error` (jobs.py) его нет, поэтому чат
  даже не вычищается — рассылка стоит на нём вечно и каждый 30 сек подтверждает Telegram,
  что перед ним спамер.
- Постер (`_poster_tick`): чат с `PeerFlood` выкидывается из круга, **остальные продолжают
  отправляться** — ограничение игнорируется.
- Веер (`_broadcast`, jobs.py:787): то же самое — продолжает по остальным чатам.
- Инвайт (`invite_collected`, jobs.py:1389): `PeerFlood` → `failed += 1`, пометка
  `invite_error` → **переход к следующему человеку**. Инвайты под активным `PeerFlood` —
  прямой путь к заморозке.
- Очередь (`queue.py`): `PeerFlood` — подкласс `RPCError` → ретрай с экспонентой
  (2с, 4с) → повторная попытка сразу после ограничения.

**Почему это и есть спамблок:** `PeerFloodError` Telegram возвращает, когда аккаунт уже
помечен за спам («писать незнакомым нельзя»). Правильная реакция — **остановить все
отправки аккаунта на часы** и сказать человеку. Сейчас код делает противоположное.

**Что делать:**
- Отдельный `except PeerFloodError` во всех путях отправки (рассылка, постер, веер,
  инвайт, очередь): ставить **circuit breaker на аккаунт** (все задачи аккаунта на паузе
  минимум на 6–12 часов, а не одна задача на 30 сек), писать в карточку задачи и в личку
  человеческим текстом: «Telegram ограничил аккаунт за спам, задачи на паузе до …».
- Не ретраить `PeerFlood` никогда (ни экспонентой, ни через 30 сек).

### 2. Рассылка: дефолтный темп — спам-паттерн
**Где:** `filters.py` (`gap_seconds=5`, `cycle_seconds=10`), `jobs.py:337`
(`MAILING_MIN_GAP = 1`), `webapp_api.py:916–924` (валидация `max(0, …)` — минимум не
ограничен), `webapp/app.js:164` (плейсхолдеры 5/10).

**Арифметика:** 150 чатов × 5 сек ≈ 12 минут на круг, через 10 сек — следующий круг
теми же текстами. При `gap=1` (разрешён!) — 150 одинаковых сообщений за 2.5 минуты.
Идентичный текст во множество чатов подряд с машинными интервалами — ровно то, по чему
Telegram определяет спам. Дневной лимит тут не спасает: спамблок прилетает по
**скорости и одинаковости**, а не по итогам суток.

**Что делать:**
- Минимум `gap_seconds`: **30–60 сек** жёстко (не 1 сек). Дефолт 60–120 сек.
- Дефолт `cycle_seconds`: **часы, а не 10 сек** (напр. 3600).
- Дефолтный `gap_jitter`: 30–50% от gap (сейчас 0 — интервалы метрономом).
- В UI: предупреждение при gap < 60 («риск спамблока») и блокировка значений < 30.

### 3. Автоподписка: вступление во всё залпом, лимиты не выведены в форму
**Где:** `jobs.py:135` (`JOIN_PAUSE_SECONDS = 2`), `filters.py`
(`join_gap=2`, `join_limit=0`, `daily_join_limit=0` — всё «без лимита»),
`webapp_api.py:843–846` (ветка `autosubscribe` принимает **только** `subscribe_to`,
`join_gap`/`join_limit`/`daily_join_limit` из payload игнорируются),
COMMANDS `autosubscribe` (`optional: ["source"]` — полей темпа нет ни в API-справочнике,
ни в форме `webapp/app.js:645`).

**Что происходит:** один запуск = вступление во все каналы списка + ссылки из 20 последних
постов источника (`run_autosubscribe`, jobs.py:1636), с паузой 2 сек (а можно и 0 —
`max(0, …)`). 50 вступлений за ~2 минуты для Telegram = ботнет-паттерн = мороз.
Пользователь при этом **физически не может** выставить безопасный темп — полей нет в UI,
API их отбрасывает.

Дополнительно: `daily_join_limit` считается **на задачу** (`repo.count_joins_today(rule_id)`),
а не на аккаунт. Три задачи автоподписки = тройной темп мимо лимита.

**Что делать:**
- Вывести `join_gap` / `join_limit` / `daily_join_limit` в форму автоподписки и в API-ветку
  (сейчас они есть только у рассылки для её `subscribe_links`).
- Безопасные дефолты: `daily_join_limit ≈ 10–15`, `join_gap` минимум 30–60 сек,
  `join_limit` за запуск ≈ 10.
- Считать вступления **на аккаунт**, а не на задачу (или добавить аккаунтный потолок).
- Дедуп: не пытаться вступать повторно в чаты, где уже участник / уже отправлена заявка
  (сейчас каждый запуск долбит по всему списку заново).

### 4. Веер (`broadcast`): вообще без пауз между чатами
**Где:** `_broadcast`, jobs.py:787 — цикл `for target in targets: send_copy(...)`,
ни одного `sleep` (проверено: все `asyncio.sleep` в jobs.py — typing/join/parser, в веере
нет).

**Что происходит:** пост из источника уходит в 150 чатов со скоростью сети подряд.
Это быстрее и опаснее рассылки. Лимитер очереди (`SEND_MIN_INTERVAL_SECONDS=1.2`)
не помогает: он срабатывает **один раз на задачу** перед хендлером, а внутри хендлера
N отправок идут без ограничений.

**Что делать:** пауза между чатами как у постера (`POSTER_CHAT_GAP`), но больше —
минимум 5–10 сек + джиттер. Веер в 150 чатов должен идти ~15–25 минут, а не 30 секунд.

### 5. Все аккаунты связаны: один api_id + один IP + один отпечаток
**Где:** `manager._new_client` (manager.py:355): `device_model="MacBook Pro"`,
`system_version="macOS"`, `app_version="1.0"` — **одинаковые у всех**;
`settings.proxy` — один прокси на весь сервис (`TelegramAccount` вообще не имеет поля
прокси); сервисные `API_ID/API_HASH` общие для всех пользователей.

**Почему это «морозят пачкой»:** одинаковый api_id + IP + fingerprint — это признаки,
по которым Telegram кластеризует аккаунты как одну ферму. Спам одного пользователя →
подозрение на всех → заморозки у непричастных. Механизм своих ключей (`LoginCreds`)
уже есть, но в UI не продвигается.

**Что делать:**
- Поле `proxy` на аккаунт (миграция + форма) — разные IP/прокси у разных пользователей.
  Это самая дорогая, но и самая важная мера против массовых заморозок.
- Рандомизация fingerprint на аккаунт (модель устройства, версия приложения) при создании
  сессии.
- Продвигать свои API-ключи в UI («меньше риск лимитов») — механизм уже готов.
- Мониторинг: алерт, когда за сутки отвалилось >N аккаунтов (сейчас `watch_offline`
  считает «не в сети», но не «умерли сегодня»).

## P1 — высокий приоритет

### 6. Рассылка/постер/веер обходят очередь доставки
`_mailing_tick` и `_poster_tick` шлют напрямую через `client.send_message`, мимо
`DeliveryQueue` с её per-account лимитером. Итог: 3 рассылки на одном аккаунте =
3 сообщения в секунду + параллельно пересылка через очередь. Никакого общего темпа
на аккаунт нет.

**Делать:** единый per-account rate limiter (напр. «не чаще 1 отправки в 20–30 сек
суммарно по всем задачам-рассылкам»), через который идут mailing/poster/broadcast.

### 7. `daily_cap` снимается одной цифрой
**Где:** `webapp_api.py` — `filters["daily_cap"] = max(0, _as_int(...))` — **верхней
границы нет**. `send_cap_for` (forwarder.py:51): любой `override > 0` полностью
перекрывает прогрев (закреплено тестом `test_override_wins_over_warmup` как фича).

**Что происходит:** пользователь ставит `daily_cap=999999` — и предохранитель мёртв,
включая прогрев новичка.

**Делать:** потолок override (напр. не выше 1000 и не выше прогревного ×2), либо варнинг
в UI «вы отключаете защиту».

### 8. Прогрев считается от даты подключения к сервису, а не от возраста аккаунта
`check_send_cap` берёт `TelegramAccount.created_at` — когда номер **подключили к сервису**.
Свежесозданный спам-номер, подключённый месяц назад, получает полный лимит 1000/сутки.
И наоборот, 5-летний аккаунт, подключённый вчера, душится до 50.

**Делать:** честно зафиксировать ограничение; дополнительно смотреть на «возраст первой
активности через нас» и резать дефолты для всех (см. п.2–3). Идеально — эвристика
«новый аккаунт = тот, кто за неделю через нас отправил мало» вместо даты строки.

### 9. `DAILY_CAP_DEFAULT = 1000` недостижим безопасно
Тысяча одинаковых сообщений в чужие чаты за сутки — это спамблок задолго до полуночи
для любого аккаунта. 1000 имеет смысл только для **своих** каналов (forward в свой канал).

**Делать:** разделить лимиты — свой чат/канал vs чужие чаты. Для рассылки по чужим чатам
дефолтный потолок порядка 30–80/сутки.

### 10. Рассылка шлёт байт-в-байт одинаковые тексты
`uniquify` и `translate_to` доступны только `forward/broadcast/clone`
(webapp_api.py:1006–1013), но **не** `poster/mailing`. `random_pick` выключен по
умолчанию, библиотека идёт по кругу. Одинаковый текст = сильнейший спам-сигнал.

**Делать:** спинтакс `{вариант1|вариант2}` в текстах рассылки + случайный невидимый хвост /
уникализация для poster/mailing; `random_pick=true` по умолчанию при >1 сообщения.

### 11. `mention_all` в рассылке — магнит для жалоб
До 30 невидимых упоминаний на сообщение (`MENTION_CAP`, jobs.py) в чужих чатах.
Люди жалуются → жалобы = спамблок. Галочка есть у рассылки/постера/веера без единого
варнинга.

**Делать:** предупреждение в UI («высокий риск жалоб и спамблока»), по умолчанию выкл
(уже), возможно капча-подтверждение.

### 12. `SlowModeWaitError` не чтится
Медленный режим чата возвращает секунды ожидания, код отвечает ретраем через фикс.
30 сек (`MAILING_ERROR_PAUSE`) независимо от требуемого → повторные нарушения.

**Делать:** обрабатывать как `FloodWait` — ждать ровно столько, сколько просят.

### 13. Мёртвая сессия = вечный ретрай
`AuthKeyDuplicated` / `SessionRevoked` / `UserDeactivated` / `PhoneNumberBanned` в тике
рассылки падают в generic `except` → 30 сек → повтор **бесконечно**, позиция не двигается,
журнал пухнет. Аккаунт уже мёртв, а задачи «работают».

**Делать:** по этим ошибкам — гасить аккаунт с причиной «подключите номер заново»
(как `SESSION_REVOKED` в `start_account`) и останавливать его задачи, а не ретраить.

### 14. Стриминговая автоподписка без дедупа и лимита
`_autosubscribe` (потоковый хендлер): на **каждое** сообщение со ссылками — заходы,
одни и те же ссылки при каждом посте → повторные `JoinChannelRequest`; `join_gap` спит
**внутри воркера очереди**, занимая слот отправки; дневной лимит по умолчанию выключен.

**Делать:** дедуп «куда уже вступали/пытались за сутки», дефолтный daily limit (п.3),
вынести сон из воркера.

## Что уже сделано хорошо (не ломать)

- `FloodWait` соблюдается целиком везде: рассылка, постер, очередь, джоины (ретрай только
  коротких ≤60 сек — правильно).
- Дневные счётчики отправок **на аккаунт** (`SendCounter`), учёт реальных отправок.
- Прогрев новичков 50 → 150 → 400 → 1000 (идея верная, см. п.8 про базу возраста).
- Очередь доставки с per-account темпом, экспоненциальными ретраями, восстановлением
  после рестарта — для пересылки всё грамотно.
- Авточистка мёртвых чатов (3 страйка), `subscribe_done`-механика, `join_limit`/`retries`
  как механизмы — осталось включить безопасные дефолты и вывести в UI.
- Свои API-ключи (`LoginCreds`) — готовый механизм развязывания, надо продвигать.
- `ApiIdPublishedFlood` при входе обрабатывается (`accounts_login.py`).

## Предлагаемый план

**Итерация 1 (останавливает активный урон):**
1. `PeerFloodError` → circuit breaker на аккаунт + понятный текст человеку (п.1).
2. Безопасные дефолты рассылки: min gap 30–60с, дефолт 60–120с, cycle — часы (п.2).
3. Пауза между чатами в веере (п.4).
4. `SlowModeWait` как `FloodWait` (п.12); мёртвая сессия → гасить аккаунт (п.13).

**Итерация 2 (автоподписка):**
5. Поля темпа в форму + безопасные дефолты + лимит на аккаунт + дедуп (п.3, п.14).

**Итерация 3 (стратегическое):**
6. Прокси на аккаунт + рандомизация fingerprint (п.5).
7. Единый per-account лимитер (п.6), потолок `daily_cap` (п.7), раздельные лимиты
   свои/чужие чаты (п.9), спинтакс для рассылки (п.10).

Каждый пункт итераций 1–2 — это 1–3 небольших коммита с тестами (рядом уже лежат
`test_antiban.py`, `test_mailing.py` — есть куда дописывать).
