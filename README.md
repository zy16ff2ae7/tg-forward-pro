# Telegram Auto-Forward — сервис автопересылки с абонементом

Сервис в духе Garvis: пользователь заходит в Telegram-бота, подключает свой аккаунт по номеру
телефона, создаёт правила «источник → приёмник» — и посты пересылаются автоматически 24/7.
Доступ продаётся абонементом на 1 месяц.

## Что умеет

| Возможность | Описание |
|---|---|
| Пересылка без метки | Пост публикуется как свой, без «Переслано от…» (режим «копия») |
| Вход по номеру | Код из Telegram + облачный пароль 2FA, сессия хранится зашифрованной |
| Несколько аккаунтов | Сколько угодно номеров на одного пользователя |
| Фильтры | Стоп-слова, белый список, типы медиа, минимальная длина |
| Чистка текста | Вырезание ссылок и @упоминаний, пропуск чужих репостов |
| Автозамены | Подмена слов и ссылок (например, партнёрские ссылки на свои) |
| Задержка | Пауза перед публикацией, чтобы не выглядеть как робот |
| Подпись | Произвольный текст в конце каждого поста |
| Оплата | Telegram Stars, карта/СБП (ЮKassa), USDT TRC-20, вручную через админа |
| Мини-апп | Кабинет внутри Telegram: команды, задачи, чаты, аккаунты |
| Копилка подписки | Дни не сгорают: можно заморозить и вернуть на любой аккаунт |

## Автоматизации (8 команд)

Помимо пересылки есть задачи, которые ставятся из мини-аппа или меню бота.
Каждая — отдельный тип (`Rule.kind`) поверх того же движка пересылки:

| Команда | Что делает |
|---|---|
| 🔁 Копирование канала | Пересылка новых публикаций между каналами с заменами текста |
| 📢 Рассылка | Отправка своего сообщения по списку чатов |
| 👥 Парсер аудитории | Сбор участников чата, дедупликация, отсев ботов |
| ✅ Автоподписка | Подписка на каналы из списка |
| 🧾 Ловец чеков | Отслеживание сообщений от `@send` |
| 🔔 Уведомления | Реакция на ключевые слова в выбранных диалогах |
| 🎣 Байтинг | Автоответ на новые сообщения в чате |
| 🔇 Мут | Игнорирование сообщений по правилам |

Готовые задачи уходят в архив (`Rule.archived`, `/api/tasks?status=done`),
любую можно запустить вручную и посмотреть результаты.

Команды показывают статус **«включено»** только когда реально работают:
он считается на лету из `settings.public_login_enabled` (= `mtproto_ready`),
а не берётся из справочника. Без `API_ID`/`API_HASH` все восемь уходят
в **«на настройке»** — кабинет при этом работает полностью. Так пользователь
не тратит время на форму, которая всё равно не сохранится.

## Как это работает технически

- **Бот-интерфейс** — aiogram 3: меню, FSM-диалоги, инвойсы Stars.
- **Чтение источников** — Telethon (личный аккаунт). Именно поэтому можно пересылать
  из чужих каналов: бот на Bot API так не умеет, а аккаунт — да.
- **Публикация** — тем же аккаунтом: скачиваем медиа и отправляем заново (`send_file`),
  либо обычным `forward_messages`, если выбран режим «форвард».
- **Хранение** — SQLAlchemy 2 (SQLite по умолчанию, PostgreSQL — одной строкой в `DATABASE_URL`).
  Схема обновляется сама: `ensure_schema()` добавляет недостающие колонки без потери данных.
  SQLite принудительно работает в **WAL** (`busy_timeout=10s`) — без этого на файловых
  системах с запрещённым `unlink` коммиты падают с `disk I/O error`.
- **Транзакции** — запись только через `session_scope()`: коммит при успехе, откат при
  исключении. Открывать `SessionLocal()` напрямую и писать без commit нельзя — при выходе
  из блока всё откатывается, и счётчики пересылок/журнал молча теряются. За этим следит
  тест `tests/test_persistence.py` (AST-проверка всего дерева `app/`).
- **Фон** — отдельные asyncio-задачи: обновление кэша правил (раз в минуту),
  проверка оплат (USDT через TronGrid, карта через ЮKassa) и напоминания
  о продлении — раз в 5 минут. Ссылку на задачу держим в модуле и отменяем
  на shutdown: без этого цикл писал в уже закрытую БД.
- **Мини-апп** — `app/webapp_api.py` раздаёт `webapp/` (чистый JS без сборки) и JSON-API.
  Авторизация — проверка подписи `initData` (HMAC-SHA256, TTL 24 часа). Вне Telegram
  кабинет открывается в демо-режиме на моках.
- **Ошибки** — единый контур `app/errors.py`: любые сбои API превращаются в JSON
  `{"error": "…"}` с корректным кодом (400/404/409/503/500), а исключения в хендлерах
  бота не оставляют пользователя с мёртвой кнопкой.
- **Логи** — loguru, уровень из `LOG_LEVEL` (TRACE…CRITICAL). Пишутся в stderr и
  в `logs/app.log` (ротация 10 МБ, хранение 14 дней). Конфигурируются **до** первого
  обращения к логгеру, поэтому падение на невалидном ключе видно сразу при старте.

### Очередь доставки

Входящее сообщение не уходит в Telegram сразу, а встаёт в очередь
(`app/telegram_client/queue.py`). Раньше каждое сообщение порождало отдельную
`asyncio.create_task` — сто постов, залетевших в канал разом, отправлялись
одновременно, скопом ловили FloodWait и терялись при перезапуске. Очередь
держит темп и границы:

| Что | Чем управляется | По умолчанию |
|---|---|---|
| Воркеры, разбирающие очередь | `DELIVERY_WORKERS` | 4 |
| Размер очереди (дальше — отброс) | `DELIVERY_QUEUE_MAXSIZE` | 2000 |
| Одновременных отправок на сервис | `SEND_GLOBAL_CONCURRENCY` | 8 |
| Минимальная пауза между отправками **одного аккаунта** | `SEND_MIN_INTERVAL_SECONDS` | 1.2 |
| Повторов при ошибке Telegram | `SEND_RETRY_ATTEMPTS` | 2 |
| База паузы между повторами | `SEND_RETRY_BASE_SECONDS` | 2.0 |
| Предел ожидания при FloodWait | `FLOOD_WAIT_MAX_SECONDS` | 900 |

Темп считается на каждый аккаунт отдельно — так же, как его считает сам
Telegram. Общая пауза на весь сервис замедляла бы одного пользователя из-за
активности другого: два аккаунта по одному сообщению ждали бы друг друга, хотя
лимита не нарушает ни один.

Как это выглядит на практике:

- **FloodWait** — ждём ровно сколько просит Telegram и повторяем. Если просят
  больше `FLOOD_WAIT_MAX_SECONDS`, не ждём: задача уходит в журнал ошибок.
- **Другие ошибки Telegram** (`RPCError`) — повтор с паузой 2 → 4 → 8 секунд.
- **Всё остальное** (БД, сеть, код) не повторяется: пять попыток упасть на
  одной и той же опечатке ничем не лучше одной.
- **Пауза держится вне слота отправки**, иначе правило, отдыхающее час по
  FloodWait, заблокировало бы остальные.
- **Задержка из правила** (`delay_seconds`) отрабатывается до постановки
  в очередь — правило с задержкой в час не занимает воркер.
- **Переполнение** — задача отбрасывается с записью в лог, а не растит память.

### Перезапуск не теряет отправки

Очередь живёт в памяти, поэтому раньше `systemctl restart` в неудачный момент
означал молча потерянные посты. Теперь задача сначала пишется в журнал ожидания
(`pending_deliveries`), и только потом уходит воркеру. Строка удаляется, когда
задача доведена до конца — отправлена, пропущена фильтром или окончательно
провалилась: иначе она повторялась бы после каждого перезапуска.

На старте сервис поднимает недоделанное (`restore_pending`): сообщение
перечитывается из источника по `message_id` — копию текста в БД не держим, там
могут быть личные переписки. Записи старше суток не восстанавливаются и
удаляются (`drop_stale_pending_deliveries`): в источнике такой пост уже
неактуален. За один раз поднимается не больше 500 отправок, чтобы после долгого
простоя в Telegram не улетела тысяча сообщений разом. Дважды одно и то же не
уйдёт: задача снимается с журнала по своему `delivery_id`.

### Что видно в мониторинге

Состояние очереди отдаёт `GET /api/health` (без авторизации, для мониторинга):

```json
{"ok": true, "service": "tg-forward",
 "delivery": {"submitted": 12, "dropped": 0, "sent": 9, "failed": 0,
              "skipped": 3, "restored": 0, "queued": 0, "workers": 4,
              "pending_delays": 0, "persisted": 0,
              "skips": {"filtered": 2, "no_subscription": 1}}}
```

Пропуски идут с разбивкой по причинам, потому что лечатся они по-разному:

| Причина | Что значит |
|---|---|
| `filtered` | Не прошло фильтры правила — норма |
| `no_subscription` | У владельца правила кончился абонемент — это про деньги |
| `filter_error` | Сам фильтр упал: правило надо править |
| `service_message`, `empty_message` | Вступления, смена аватара, пустое сообщение |

Рост `queued` значит, что воркеры не справляются — пора поднимать
`DELIVERY_WORKERS` или `SEND_GLOBAL_CONCURRENCY`. Рост `failed` — смотреть
журнал пересылок в админке. Рост `persisted` при нулевом `queued` — задачи
записаны, но не разобраны: проверить, что очередь вообще поднялась.

При остановке сервиса очередь сначала дожимает то, что уже в работе
(`drain=True`, до 30 секунд), и только потом отключаются Telethon-клиенты —
иначе недоотправленное падало бы с ошибкой соединения.

## Быстрый старт локально

```bash
git clone <ваш-репозиторий> tg-forward && cd tg-forward
cp .env.example .env
```

Заполните в `.env`:

1. `BOT_TOKEN` — токен от [@BotFather](https://t.me/BotFather).
2. `API_ID` / `API_HASH` — [my.telegram.org](https://my.telegram.org) → API development tools.
3. `SECRET_KEY` — сгенерируйте: `python scripts/gen_secret.py`.
   **Потеря ключа = потеря всех сессий пользователей.**
4. `ADMIN_IDS` — ваш Telegram user_id (узнать: [@userinfobot](https://t.me/userinfobot)).

Запуск:

```bash
chmod +x run.sh deploy/deploy.sh
./run.sh          # создаст venv, поставит зависимости, запустит бота в long polling
```

Для локального запуска `WEBHOOK_URL` оставьте пустым — бот пойдёт на long polling.

Без `API_ID` / `API_HASH` приложение стартует, но вход аккаунтов отключён:
в логе будет `WARNING … бот и мини-апп стартуют, вход аккаунтов отключён`.
Всё остальное — меню, мини-апп, оплата — работает.

### Подключить уже готовый аккаунт (без кода из Telegram)

Если аккаунт где-то уже авторизован и от него осталась «сырая» сессия —
`<auth_key в hex, 512 символов>:<номер DC>` или файл `*.session` от Telethon —
получать код повторно не нужно:

```bash
# из файла Telethon (точнее всего: DC, адрес и порт берутся из файла)
PYTHONPATH=. python scripts/import_session.py \
  --file ~/Downloads/255824769_telethon.session --save --user-id 7686196719

# только проверить ключ, ничего не записывая
PYTHONPATH=. python scripts/import_session.py --session "bd64...9131:1"

# проверить и записать в базу зашифрованной
PYTHONPATH=. python scripts/import_session.py --session "bd64...9131:1" \
  --save --user-id 7686196719
```

Скрипт разбирает три формата (`hex:dc`, `hex`, готовая StringSession), упаковывает
ключ в `StringSession`, подключается, печатает `get_me()` и кладёт сессию в БД
зашифрованной Fernet-ключом.

Если есть файл `*.session` (SQLite от Telethon), из него можно достать и `auth_key`,
и точные `dc_id`/`server_address`/`port`:

```bash
sqlite3 account.session "SELECT dc_id, server_address, port, hex(auth_key) FROM sessions"
```

**Важно:** `auth_key` привязан к `api_id`, под которым он создавался. Если сессия
сделана на официальных кредах Telegram Desktop (`2040`), а в `.env` стоит другой
`API_ID` — получите `AUTH_KEY_UNREGISTERED`, в худшем случае бан аккаунта.
Свои `API_ID`/`API_HASH` + вход по номеру в боте — единственный чистый путь;
официальные креды допустимы только как временная мера (нарушают ToS Telegram).

### Перенести аккаунт на другую машину (ноутбук → VDS)

Повторно входить по номеру не нужно: сессию можно вытащить из базы и
положить в базу на новом месте.

```bash
# на исходной машине: посмотреть, что есть, и выгрузить в файл
PYTHONPATH=. python scripts/export_session.py --list
PYTHONPATH=. python scripts/export_session.py --user-id 7686196719 --out /tmp/acc.session

# на новой машине (ключ там может быть другим — не страшно, сессия
# зашифруется заново уже местным SECRET_KEY)
RAW_SESSION=$(cat /tmp/acc.session) PYTHONPATH=. python scripts/import_session.py \
  --save --user-id 7686196719
```

Сессия в `--out`-файле создаётся с правами `600`; строка даёт полный доступ
к аккаунту, поэтому не коммитьте её и не пересылайте в чаты. После импорта
перезапустите сервис — в логе появится «Аккаунт #N на связи».

### Открыть мини-апп на локальной машине

Telegram открывает Web App только по HTTPS, поэтому нужен публичный адрес:

```bash
./scripts/expose.sh          # поднимает туннель, прописывает WEBAPP_URL в .env
./scripts/expose.sh --stop   # погасить
```

Скрипт сам находит `ngrok` или `cloudflared`, ждёт HTTPS-адрес, обновляет `WEBAPP_URL`
в `.env` и печатает напоминание перезапустить бота. После перезапуска в логе появится
«Кнопка мини-аппа установлена: …» — без этой строки кнопки не будет.

> Все бесплатные туннели показывают браузерам страницу-предупреждение
> («You are about to visit…»). Telegram WebView тоже её покажет — первый раз
> нужно тапнуть «Visit Site», дальше запоминается. В продакшене нужен свой
> домен и HTTPS, либо платный тариф туннеля.

Кабинет в обычном браузере: `http://127.0.0.1:8080/app/?demo=1` (демо-данные).

## Конфигурация

Все настройки — переменные окружения (`app/config.py`), список с комментариями —
в `.env.example`. При старте приложение делит проблемы на два типа:

**Фатальные** (`settings.require()`) — процесс не поднимается, в логе явная причина:

- нет `BOT_TOKEN` или `SECRET_KEY`;
- `SECRET_KEY` — не ключ Fernet (сгенерируйте: `python scripts/gen_secret.py`);
- задан `WEBHOOK_URL`, но пуст `WEBHOOK_SECRET` — вебхук без секрета принимает
  любое поддельное обновление.

**Мягкие** (`settings.warnings()`) — работа продолжается, в логе `WARNING`:

| Ситуация | Чем грозит |
|---|---|
| Нет `API_ID` / `API_HASH` | Вход аккаунтов отключён, остальное работает |
| `ADMIN_IDS` пуст | Админ-команды недоступны |
| Не задан `WEBAPP_URL` и `WEBHOOK_URL` | Кнопка мини-аппа у бота не появится |
| ЮKassa заполнена наполовину | Оплата картой молча не поднимется |
| `PAY_MODE=external`, но адрес страницы не собрать | Карта и USDT недоступны нигде |
| `PAY_MODE=inline` с картой или USDT | Продажа внутри Telegram не за Stars — риск по п. 6.2 |
| `EXTERNAL_PAYMENTS_URL` не на `https://` | Ссылка на оплату не откроется из Telegram |
| `DELIVERY_WORKERS` < 1 | Очередь доставки не сможет работать |
| `DELIVERY_QUEUE_MAXSIZE` < 10 | При всплеске посты начнут отбрасываться |
| `SEND_MIN_INTERVAL_SECONDS` < 0.5 | Высокий риск FloodWait |

Значения очереди доставки поджимаются снизу (`max(1, …)`), поэтому кривое
значение не ломает запуск — но о намерении стоит напомнить.

«Половинчатые» значения не проходят молча: `mtproto_ready` отклоняет плейсхолдеры
вроде `0` или `your_api_id`, а не только пустые строки.

## Тесты

```bash
pip install -r requirements-dev.txt
pytest -q                      # весь набор
pytest -q tests/test_filters.py
pytest -q -k subscription      # по маске
```

301 тест, база — временный SQLite в `TMPDIR`, наружу не ходим, токен и ключ
шифрования поддельные: продакшен-данные не затрагиваются.

| Файл | Что проверяет |
|---|---|
| `tests/test_filters.py` | Стоп-слова, белый список, чистка текста, автозамены, граничные случаи (пустые записи списков) |
| `tests/test_subscription.py` | Абонемент: активация, продление, триал, копилка, истечение, округление дней |

| `tests/test_webapp_api.py` | Подпись `initData`: подменённый хеш, чужой токен, просрочка; коды 400/404/409/503; единый формат ошибок; счёт в Stars |

| `tests/helpers.py`, `tests/conftest.py` | Общая обвязка: подписанный `initData`, бот-заглушка, чистая схема БД на каждый тест |

### Дымовые прогоны без pytest

| Скрипт | Что проверяет | Где запускать |
|---|---|---|
| `python scripts/smoke_api.py` | Кабинет целиком: поднимает то же приложение, что `app/main.py` (те же middleware, маршруты, статика), на случайном порту `127.0.0.1` и проходит настоящим HTTP-клиентом по всем эндпоинтам и обоим контурам оплаты — 118 проверок, в конце сводка и код возврата | Локально в любой момент: база своя временная, наружу не ходит |
| `python scripts/smoke_test.py` | Слой данных: таблицы, триал, шифрование сессии, фильтры, истечение и продление абонемента | После деплоя: работает с **рабочей** базой (создаёт и удаляет тестового пользователя) |

`smoke_api.py` ловит то, чего юнит-тесты не видят: забытый маршрут, пропавший
файл в `webapp/`, HTML-трассировку вместо JSON, страницу оплаты при выключенном
контуре. Что он сознательно не делает — печатает отдельной строкой: счёт в Stars
(это вызов Bot API) и обращение к ЮKassa (вместо неё заглушка). Бот в приложение
не передаётся, поэтому всё, что требует Bot API, обязано ответить честным 503 —
это тоже проверка.

## Деплой на VDS (24/7)

Требуется: Ubuntu/Debian, домен с HTTPS (для мини-аппа — Telegram WebApp
открывается только по HTTPS) и SSH-доступ.

Бот может работать двумя способами:

- **Long polling** (по умолчанию) — `WEBHOOK_URL` пуст. Не нужен публичный
  порт, проще всего. Работает сразу после заливки.
- **Webhook** — `WEBHOOK_URL=https://YOUR_DOMAIN`, путь `/webhook`. Экономит
  запросы, но требует, чтобы сервер был доступен по HTTPS извне.

Для мини-аппа HTTPS всё равно нужен — его отдаёт nginx поверх сервиса.

```bash
# 1. На сервере один раз: nginx + certbot
sudo apt update && sudo apt install -y nginx certbot python3-certbot-nginx

# 2. В .env на сервере:
#    HOST=127.0.0.1   PORT=8080
#    WEBHOOK_URL=            # пусто → long polling
#    WEBAPP_URL=https://YOUR_DOMAIN

# 3. Заливка кода (rsync + venv + systemd), см. deploy/deploy.sh
./deploy/deploy.sh root@YOUR_SERVER

# 4. Когда домен указывает на сервер (A-запись) — выпустить сертификат.
#    То же самое, но с проверками и понятным сообщением, если записи ещё нет:
scp deploy/https.sh root@YOUR_SERVER:/opt/tg-forward/deploy/
ssh root@YOUR_SERVER bash /opt/tg-forward/deploy/https.sh YOUR_DOMAIN

#    Вручную — certbot сам допишет блок 443 и HTTPS-редирект в конфиг nginx:
sudo certbot --nginx -d YOUR_DOMAIN
```

`deploy/https.sh` идёт по шагам и останавливается там, где что-то не готово:
сначала сверяет A-запись с IP сервера (и печатает, какую именно запись
добавить у регистратора), потом проверяет конфиг nginx, выпускает сертификат
и в конце проверяет, что `https://ДОМЕН/app/` отвечает 200. Скрипт можно
перезапускать — уже выпущенный сертификат он не перевыпустит, а только
проверит срок.

Конфиг nginx — в `deploy/nginx.conf`, systemd-юнит — в `deploy/tg-forward.service`.
Важно: nginx проксирует не только `/webhook`, но и `/` — иначе мини-апп (`/app/`)
и его API (`/api/`) снаружи недоступны, потому что приложение слушает только
`127.0.0.1:8080`.

До выпуска сертификата удобно отдавать сервис по HTTP (см. блок `listen 80`
в `deploy/nginx.conf`): так видно, что он жив, ещё без HTTPS. Как только
`certbot --nginx` выпустит сертификат, он добавит `listen 443` и редирект
`301 → https` — менять ничего вручную не нужно.

При первом деплое скрипт создаст на сервере `.env` из `.env.example` и остановится:
systemd читает этот файл через `EnvironmentFile`, а ключи у вас свои. Заполните
`.env` и запустите `./deploy/deploy.sh` снова.

```bash
systemctl status tg-forward     # статус
journalctl -u tg-forward -f     # логи в реальном времени
curl -s 127.0.0.1:8080/api/health   # счётчики очереди доставки
```

### Домен без покупки (nip.io) и ловушка 443

Если своего домена нет, для мини-аппа хватит бесплатного `*.nip.io` — он
указывает на нужный IP автоматически, A-запись не нужна:

```bash
# <IP сервера> меняется на ваш; имя перед ним — любое
ssh root@YOUR_SERVER bash /opt/tg-forward/deploy/https.sh \
   papa.107-173-89-192.nip.io
```

Но на VDS порт 443 часто уже занят — например, stream-блоком nginx с
`ssl_preread`, который разбирает входящий TLS по SNI и отдаёт VPN-бэкендам
(xray/VLESS). В этом случае HTTP-сайт на `listen 443 ssl` «не слышен»: запрос
с SNI нашего домена уходит на VPN и клиент видит чужой сертификат
(в логе — соединение, но сертификат не Let's Encrypt).

Признак на сервере:
```bash
echo | openssl s_client -connect 127.0.0.1:443 -servername YOUR_DOMAIN \
  | openssl x509 -noout -issuer   # должно быть "Let's Encrypt"
```

Лечится так: сайт слушает не 443, а отдельный порт (например `8443`), а в
карту SNI stream-блока добавляется строка, которая направляет наш SNI на
этот порт:
```bash
# /etc/nginx/stream-conf.d/*.conf, внутри `map $ssl_preread_server_name`:
YOUR_DOMAIN  127.0.0.1:8443;   # перед строкой default
```
и в `deploy/nginx.conf` меняем `listen 443 ssl;` → `listen 8443 ssl;`, затем
`nginx -t && systemctl reload nginx`. `deploy/https.sh --auto-sni` делает обе
правки сам (с бэкапами).

Теперь мини-апп открывается по `https://YOUR_DOMAIN` — стандартный 443, просто
трафик нужного SNI перенаправляется на 8443 внутри сервера.

### Проверить, что пересылка действительно работает

Самый быстрый способ — правило «из чата с ботом в Избранное»:

1. Отправьте боту `/start` с того аккаунта, который подключён как источник.
2. В мини-аппе создайте задачу «Копирование канала»: источник — `@ваш_бот`,
   приёмник — `me` (Избранное).
3. Напишите боту любое сообщение и подождите пару секунд.

```bash
# сообщение ушло — счётчик sent вырос
curl -s 127.0.0.1:8080/api/health | grep -o '"sent":[0-9]*'

# и в журнале появилась строка со статусом ok
sqlite3 data/app.db "SELECT id, rule_id, source_msg_id, target_msg_id, status
                     FROM forward_logs ORDER BY id DESC LIMIT 5"
```

Правило после проверки удалите. Если `sent` растёт, а сообщения не видно —
смотрите `failed` и `journalctl -u tg-forward`: причина (FloodWait, нет прав
писать в приёмник) остаётся в логе.

> ⚠️ Рекомендуется прокси для Telethon, если VDS за пределами РФ/СНГ:
> `PROXY=socks5://user:pass@host:port` в `.env`.

## Настройка оплаты

### Два контура: звёзды в Telegram, карта и крипта на сайте

Правила Telegram (ToS для разработчиков, п. 6.2) требуют продавать цифровые
товары внутри Telegram **только за Stars**. Поэтому способы оплаты разведены по
контурам, а выбирает контур `PAY_MODE`:

| `PAY_MODE` | Внутри бота и кабинета | На странице `/pay` |
|---|---|---|
| `external` (по умолчанию) | звёзды, заявка админу | карта/СБП, USDT |
| `stars` | звёзды, заявка админу | — (карта и USDT выключены) |
| `inline` | всё, как раньше | — |

Как это выглядит для человека: в боте и в кабинете есть кнопка
«🌐 Оплатить картой или криптой на сайте». Она открывает обычную веб-страницу
`https://<домен>/pay` — в кабинете через `WebApp.openLink`, то есть во внешнем
браузере, а не в WebView Telegram. Ничего не скрыто: на кнопке и в тексте прямо
написано, что оплата уходит на страницу сервиса.

Как это устроено:

- Ссылка подписана: `t=<user_id>.<months>.<expires>.<HMAC-SHA256(SECRET_KEY)>`,
  живёт час (`app/paylink.py`). Токен ничего не читает — он даёт право выставить
  счёт **на своего же** `user_id`, иначе `/pay?user=123` позволял бы выставлять
  счёта чужим людям. Кабинет просит свежий токен (`GET /api/pay/link`) в момент
  нажатия, а не при открытии.
- Счёт выставляет тот же код, что и в боте (`app/payments/service.py`): цену
  считает сервер по каталогу сроков, клиент передаёт только `months`. Больше
  пяти неоплаченных счетов одним способом сервис не выставит.
- Доступ включается сам: фоновый цикл раз в 5 минут спрашивает у ЮKassa и
  TronGrid статус висящих счетов и присылает подтверждение в бот. Кнопки
  «Я оплатил» на странице нет — она там и не нужна.
- Брошенные счёта закрываются: карта — через 24 часа, USDT — через 72
  (`repo.expire_stale_payments`). Иначе метка-сумма USDT остаётся занятой
  навсегда, а лимит висящих счетов запирает человека без нового счёта.

`EXTERNAL_PAYMENTS_URL` нужен, только если страница живёт на другом домене;
по умолчанию адрес строится из `WEBAPP_URL`/`WEBHOOK_URL` + `/pay`. При
`PAY_MODE=inline` с настроенной картой или USDT сервис на старте пишет в лог
предупреждение о п. 6.2 — режим оставлен, но риск блокировки на вас.

> Контур снижает риск, но не убирает его совсем: Telegram смотрит и на то, что
> бот рекламирует. Оплата на стороннем сайте — обычная практика (так работают
> подписки многих сервисов), но окончательное решение всегда за платформой.

### Telegram Stars — самый быстрый старт
Ничего подключать не нужно, работает сразу. Цена — `PRICE_STARS`.
Вывод средств: через [@xRocket](https://t.me/xrocket) или Fragment.

Срок выбирается из каталога — **1, 3, 6 или 12 месяцев** (`app/plans.py`).
Он один и для бота, и для кабинета: цена считается умножением
`PRICE_STARS × months` на сервере, поэтому кнопки не расходятся со счётом.
Добавить срок — значит добавить его в `PERIODS`, и он появится в обоих местах.

Оплата из кабинета идёт не покидая мини-апп:

1. Мини-апп дёргает `POST /api/subscription/invoice` (срок — 1…12 месяцев).
2. Бэкенд сам считает сумму (`PRICE_STARS × months`) и создаёт инвойс через
   Bot API `createInvoiceLink`. Клиент передаёт только срок, не цену.
3. Мини-апп открывает ссылку через `WebApp.openInvoice`, зачисление приходит
   в хендлер `successful_payment` бота — второй реализации оплаты нет.

Вне Telegram (обычный браузер, демо-режим) `openInvoice` недоступен — кнопка
честно уводит в диалог с ботом, а не делает вид, что платёж начался.
Если Bot API недоступен, вместо 500 приходит 503 с `status: invoice_failed`.

### ЮKassa (карты, СБП)
Нужна самозанятость/ИП + договор с [ЮKassa](https://yookassa.ru). Заполните в `.env`:
`YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_RETURN_URL`.
При `PAY_MODE=external` (по умолчанию) карта работает на странице `/pay`,
а доступ включает фоновая проверка статуса платежа.

### USDT (TRC-20)
Укажите `USDT_TRC20_WALLET` и, желательно, `TRONGRID_API_KEY`.
Каждому платежу выдаётся **уникальная сумма** (например `12.017` вместо `12.00`) —
по ней сервис сам находит перевод и включает доступ.

### Вручную
Кнопка «Через администратора» шлёт заявку вам в личку, вы выдаёте доступ командой
`/grant <user_id> <месяцев>`.

## Интерфейс мини-аппа

Кабинет — `webapp/` (HTML + CSS + JS, сборка не нужна). Лицо сервиса — персонаж
**Папа, ночной портье**: он же маскот в шапке, на экране загрузки и в состоянии
ошибки. Один и тот же SVG-символ `<symbol id="papa">`, подключаемый через `<use>`
— правится в одном месте.

Что есть в интерфейсе:

- **Состояния загрузки** — скелетоны вместо пустого экрана; показываются только
  при первой загрузке списка, поэтому переключение вкладок не мигает.
- **Состояния ошибок** — вместо «ничего не найдено» блок с Папой, текстом причины
  и кнопкой «Повторить» (`data-retry` слушается делегированием).
- **Занятые кнопки** — `withLoading()` крутит спиннер и блокирует повторный тап,
  метка кнопки сохраняется.
- **Адаптивность** — колонка центрируется на широких экранах, а кнопки переносятся
  всегда, а не по медиазапросу: обычный экран в Telegram — 390 px, и это не «узкий
  случай». Ряд подписки — сетка `1fr 1fr` с оплатой звёздами во всю ширину, ряд
  действий задачи переносится сам, корзина держит свой столбец.
- **Свежесть после выката** — ссылки на `styles.css` и `app.js` (и адрес самого
  кабинета в кнопках бота) содержат `?v=<метка сборки>`; метка считается по
  содержимому файлов (`app/webapp_build.py`). Без этого Telegram WebView отдаёт
  вёрстку из своего кэша, и деплой «не виден»: HTML уходит с `Cache-Control:
  no-store`, статика без метки — с `no-cache`, а с меткой — `immutable`.
- **Доступность** — контраст текста к фону не ниже 5.6:1 (`--muted` — 7.45:1, AAA),
  видимый фокус на всех интерактивных элементах (для срезанных `clip-path` углов —
  внутренняя рамка через `box-shadow: inset`, внешний `outline` бы обрезался),
  `prefers-reduced-motion` полностью выключает анимации.
- **Производительность** — анимируются только `transform` и `opacity`, шиммер
  скелетонов сделан на `translateX`, а не на `background-position`.
- **Оплата звёздами** — кнопка сама показывает цену (`⭐ Оплатить 299 звёзд`,
  сумма приходит в `/api/me` вместе с тарифами) и открывает инвойс поверх
  кабинета: `paid`/`pending`/`failed` — тост, `cancelled` — молчим.
- **Оплата на сайте** — отдельная кнопка «🌐 Оплатить картой или криптой на
  сайте» появляется только если контур включён (`pay.external` в `/api/me`).
  Открывает страницу `/pay` через `WebApp.openLink` — во внешнем браузере,
  не в WebView Telegram.

> **Уточнение про «мини-карту».** Никакой карты в проекте нет: ближайшее совпадение
> в коде — кнопка «💳 Карта / СБП» (это способ оплаты) и вызовы `Array.map()`.
> Анимацию загрузки добавил туда, где она действительно нужна, — в мини-апп:
> скелетоны списков и экран загрузки с Папой.

## Юридические и технические нюансы

- Сервис работает через личные аккаунты пользователей — это разрешено Telegram, но
  **злоупотреблять нельзя**: ставьте задержки, не делайте тысяч пересылок в час,
  иначе аккаунт ловит `FloodWait` или ограничения.
- Цифровые товары внутри Telegram продаются только за Stars (ToS для
  разработчиков, п. 6.2). Поэтому по умолчанию (`PAY_MODE=external`) карта и
  крипта живут на странице сервиса вне Telegram, а внутри бота остаются звёзды.
  Это снижает риск, но не отменяет его: смотрят и на то, что бот рекламирует.
- Альбомы (несколько фото одним постом) приходят как отдельные сообщения —
  они пересылаются по одному. Это стандартное поведение и для коммерческих аналогов.
- Медиа больше 50 МБ не скачивается для «чистой» пересылки — уходит обычным форвардом.
- Сессии шифруются Fernet-ключом. Держите `SECRET_KEY` в секрете и в бэкапе.
  Им же подписываются ссылки на оплату (`app/paylink.py`): смена ключа
  обесценивает выданные ссылки — это нормально, они живут час.

### Полезные мелочи

- `utils.smart_edit()` — правка сообщения с учётом медиа: если у сообщения есть
  фото, правится `caption`, иначе `text`. Без этого все кнопки меню молча
  перестают работать после `/start` с баннером (Telegram: «there is no text in
  the message to edit»).
- Если `assets/welcome.png` нет, `/start` отправляет текстовое приветствие —
  баннер необязателен.
