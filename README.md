# Telegram Auto-Forward — сервис автопересылки с абонементом

Сервис в духе Garvis: пользователь заходит в Telegram-бота, подключает свой аккаунт по номеру
телефона, создаёт правила «источник → приёмник» — и посты пересылаются автоматически 24/7.
Доступ продаётся абонементом на 1 месяц.

## Что умеет

| Возможность | Описание |
|---|---|
| Пересылка без метки | Пост публикуется как свой, без «Переслано от…» (режим «копия») |
| Вход: номер или QR | Код из Telegram или скан QR-кода + облачный пароль 2FA; можно своими ключами API, сессия и hash шифруются |
| Несколько аккаунтов | Сколько угодно номеров на одного пользователя |
| Фильтры | Стоп-слова, белый список, типы медиа, минимальная длина |
| Чистка текста | Вырезание ссылок и @упоминаний, пропуск чужих репостов |
| Автозамены | Подмена слов и ссылок (например, партнёрские ссылки на свои) |
| Задержка | Пауза перед публикацией, чтобы не выглядеть как робот |
| Подпись | Произвольный текст в конце каждого поста |
| Оплата | Telegram Stars, карта/СБП (ЮKassa), USDT TRC-20, вручную через админа |
| Мини-апп | Кабинет внутри Telegram: команды, задачи, чаты, аккаунты |
| Библиотека сообщений | Свои тексты и готовые посты в одном месте — из них берёт сообщения рассылка |
| Копилка подписки | Дни не сгорают: можно заморозить и вернуть на любой аккаунт |
| Дни за подписку на канал | Разовый подарок: подписался на канал сервиса — получил N дней работы задач |

## Автоматизации (9 команд)

Помимо пересылки есть задачи, которые ставятся из мини-аппа или меню бота.
Каждая — отдельный тип (`Rule.kind`) поверх того же движка пересылки:

| Команда | Блок | Что делает |
|---|---|---|
| 🔁 Копирование канала | чужие посты | Один канал — в один ваш, с заменами текста |
| 📣 Пересылка в несколько чатов | чужие посты | Тот же пост из источника — сразу во все выбранные чаты, одним залпом |
| 📤 Постинг и рассылка | свои сообщения | Ваше объявление по чатам: по расписанию — каждые N минут в окне времени, по очереди — чат, пауза, следующий. Механика — переключателем в форме |
| 👥 Парсер аудитории | аудитория | Сбор участников чата или авторов сообщений, фильтры (юзернейм, админы, Premium, аватарка, активность), дедупликация, отсев ботов |
| ✅ Автоподписка | аудитория | Подписка на каналы из списка |
| 🧾 Ловец чеков | входящее | Отслеживание сообщений от `@send` |
| 🔔 Уведомления | входящее | Входящие личные сообщения в выбранный чат; боты, архив и мут пропускаются (галочки снимаются) |
| 🎣 Байтинг | модерация | Автоответ на новые сообщения в чате |
| 🔇 Мут | модерация | Игнорирование сообщений по правилам |

### Три задачи «в чаты» — и чем они различаются

Три команды кладут сообщение в список чатов, и по прежним описаниям читались
как одна и та же задача. Постинг и рассылка при этом вообще один слот
(`sender`): расписание и очередь — это «как слать», а не разные задачи, и
переключаются в форме (поле `send_mode`, в движке `kind` poster/mailing).
Различают слоты два вопроса: **чей** текст уходит и **как** он расходится по
чатам. Отсюда три вещи в каталоге:

- **блоки** (`COMMAND_GROUPS`) — «чужие посты» отделены от «свои сообщения»:
  первым нужен источник, вторым — текст в форме;
- **описание** начинается с того, чем команда отличается от соседней, а не с
  общего «шлёт в чаты»;
- **метки** в подвале карточки (`tags`, две-три на команду) — короткий ответ на
  оба вопроса: `чужие посты · все чаты разом · по факту поста` против
  `ваш текст · по одному чату · пауза и круги`.

Названия «постинг по расписанию» и «рассылка по очереди» стоят везде, где
пользователь их видит: каталог, карточка задачи (`jobs.task_title`), «Что умею»
в боте, заголовок формы. Проверки на непохожесть — в трёх слоях сразу
(`tests/test_webapp_api.py`, `scripts/smoke_api.py`, визуальный прогон), иначе
двойники вернулись бы первой же правкой текста.

Подписи блоков нарочно короткие: они же стоят чипсами над списком, а на 390 px
длинная фраза уезжает за край экрана.

Готовые задачи уходят в архив (`Rule.archived`, `/api/tasks?status=done`),
любую можно запустить вручную и посмотреть результаты.

### Сколько угодно чатов в одной задаче

Пересылка, постинг, рассылка и автоподписка берут **список** чатов, а не
один. Ограничения на длину списка нет: у пересылки нет отдельного поля
«Приёмник», у постинга — «Чат», у всех одно поле «Чаты».

Геометрия у списка одна на все задачи, потому что колонка `Rule.target_id`
обязательная: первый чат ложится в неё, остальные — в `filters["targets"]`.
Собирать их обратно вручную нельзя, читать список можно только через
`jobs.chat_recipients(rule)` — иначе первый чат теряется, и задача, которую
кабинет обещал на 150 чатов, ходит в 149. Раскладывает список
`_split_chats(pairs, source_id)`: убирает повторы и **источник** — пересылать
пост в тот же чат, откуда он взят, незачем.

Поиск чатов по ссылкам — один на всю задачу: `manager.resolve_many(account_id,
queries)` проходит диалоги **один раз** и разбирает сразу весь список. Отдельный
`resolve_chat` на каждую ссылку означал бы 150 обходов диалогов на одну форму и
FloodWait от Telegram. Список диалогов кэшируется на `DIALOGS_CACHE_TTL` (60 сек)
и сбрасывается в `stop_account`, а `list_dialogs(limit=0)` отдаёт все чаты без
верхней границы.

Отправка по большому списку не идёт залпом: постер за тик берёт не больше
`POSTER_BATCH` чатов с паузой `POSTER_CHAT_GAP` между ними и укладывается
в `POSTER_TICK_BUDGET`, недоотправленные остаются в очереди правила. Иначе
задача с сотней чатов занимала бы цикл целиком и остальные ждали бы её.

Одно исключение из поиска — **автоподписка**: ненайденный канал для неё норма,
а не ошибка. В диалогах аккаунта его нет именно потому, что вступать в него ещё
предстоит, а ссылку-приглашение (`t.me/+…`) до вступления не разрешает вообще
никто. Раньше форма отвечала на такие ссылки 404 «не нашёл чат» — то есть
задача не создавалась ровно в том случае, для которого её и заводят. Теперь
список уходит в `filters["subscribe_to"]` как есть и разбирается уже при
вступлении (`run_autosubscribe`). Ошибку по **источнику** это не отменяет: из
него читают ссылки на каналы, и без доступа задача бесполезна.

Команды показывают статус **«включено»** только когда реально работают:
он считается на лету из `settings.public_login_enabled` (= `mtproto_ready`),
а не берётся из справочника. Без `API_ID`/`API_HASH` все десять уходят
в **«на настройке»** — кабинет при этом работает полностью. Так пользователь
не тратит время на форму, которая всё равно не сохранится.

### Рассылка по очереди и библиотека сообщений

Рассылка — единственная задача, которая сама решает, когда отправлять: входящих
сообщений она не ждёт, а ходит по списку получателей. Планировщик у неё свой
(`manager._mailing_tick`, тик раз в секунду), и за один проход уходит **одно**
сообщение **одному** получателю — темп задают паузы, а не скорость цикла:

- `gap_seconds` (+ `gap_jitter`) — пауза между чатами, `cycle_seconds`
  (+ `cycle_jitter`) — перед новым кругом. Джиттер только **прибавляется**:
  человек задал минимум, уходить ниже него — прямой путь под ограничения.
- `repeats` — сколько кругов сделать. `0` (и не заданное значение) — крутить,
  пока не остановят; сделав заданное число кругов, задача сама встаёт на паузу.
  Снятая с паузы исчерпанная рассылка начинает круги заново.
- Позиция в круге выводится из `Rule.forwarded_count`, поэтому перезапуск
  процесса продолжает рассылку с того же чата, а не с начала круга.
- `FloodWait` от Telegram соблюдается целиком, ошибка в одном чате не роняет
  задачу, а пустая библиотека — это пауза, а не поток предупреждений в журнале.

Сами сообщения живут в библиотеке (`saved_messages`, эндпоинты `/api/library`):
тексты из формы задачи ложатся туда сразу при создании, дальше их можно
пополнять и удалять, не пересоздавая задачу. По кругу они идут в том порядке,
в каком добавлены; `random_pick` берёт наугад, `typing` показывает «печатает»
перед отправкой.

В кабинете у библиотеки свой экран («Ещё» → «Библиотека сообщений»): там текст
сохраняют один раз, а в форме рассылки отмечают мышкой кнопкой
«📚 из библиотеки». Отмеченные уходят в задачу **ссылками** (`library_ids`),
а не копией текста, поэтому:

- поле «Сообщение» при выбранной библиотеке можно оставить пустым — так считают
  и кабинет, и сервер (`create_task`), иначе один и тот же текст плодил бы
  записи-двойники;
- список читается **на каждом тике** (`load_mailing_library`), значит
  пополненная библиотека меняет уже работающую задачу;
- удалённые и чужие id молча отбрасываются — задача продолжает работать
  на том, что осталось.

### Сообщения делит пустая строка, а не каждый перенос

Поле «Сообщение» у постинга и рассылки принимает несколько сообщений сразу, и
раньше границей служил любой перенос строки. Прайс в четыре строки —

```
Приму 1 код,момент
4000 - 552
Приму 1 код,момент
4500 - 585
```

— уходил четырьмя обрывками вместо одного объявления. Теперь границей служит
**пустая строка**: одиночный перенос остаётся внутри сообщения, разделяют только
две и больше подряд (`\r\n` и строки из пробелов тоже считаются пустыми). Правило
одно на обе стороны — `_split_messages` в `app/webapp_api.py` и `splitMessages`
в `webapp/app.js` — иначе кабинет обещал бы одно, а сервер сохранял другое.

Что из этого видно в форме:

- под полем счётчик «N сообщений» и заголовок первого — первая непустая строка,
  обрезанная до 48 знаков (`_message_title`). Так видно **до** отправки, что
  прайс уйдёт целиком, а не столбиком;
- подсказка под полем говорит правило прямо: «пустая строка делит сообщения,
  простой перенос — нет»;
- в библиотеке заголовком записи становится та же первая строка, поэтому список
  сохранённых текстов читается, а не выглядит набором одинаковых начал.

### Шаблоны и мастер новичка

Каталог начинается с шаблонов: зеркало канала, охотник за скидками, чистая
копия, веер новостей, сбор комментаторов. Нажатие открывает форму создания
с готовой начинкой — остаются только аккаунт и чаты.

- **Шаблоны не протухают.** Тест проверяет, что каждая ссылка ведёт на
  живую команду, а каждое поле — в её форму.
- **Мастер вместо пустого экрана.** Пока нет задач, главная показывает два
  шага — подключить аккаунт и выбрать сценарий. Исчезает сам с первой
  задачей.
- **Первая задача за минуту.** Кнопка мастера открывает визард из трёх
  шагов — откуда, куда, запуск: чаты выбираются из списка, дальше проверка
  и пуск. Окна «когда» нет осознанно: пересылка идёт в реальном времени.

### Чистка мёртвых получателей

Три безнадёжных сбоя подряд (выгнали, чат снесён, писать запрещено) — и
чат уходит из получателей сам: веер, постинг и рассылка больше об него не
спотыкаются. Уборка видна в журнале и счётчиком на карточке.

- **Только безнадёжное.** Сеть, слоумод и временные отказы страйков не
  дают: три глюка подряд — ещё не мёртвый чат.
- **Главный приёмник — руками.** Авто-уборка трогает только список
  получателей; смерть главного — задача для человека, о ней пишут алерты.
- **Оживший прощается.** Чат снова принял сообщение — страйки с него
  снимаются.

### График пересылок

Главная кабинета показывает две недели столбиками: сколько ушло в каждый
день. Ошибки — красным верхом столбика: больной день видно сразу, без
открытия журнала. Под графиком — итог, счёт ошибок и топ-5 задач.

- **Без библиотек.** Чистый SVG: нечего грузить, нечему ломаться.
- **Тихо при пустоте.** Нет пересылок — нет графика: нулевые столбики
  никому не нужны. Не загрузился — главная всё равно работает.

### Письма о больных задачах

Третья ошибка подряд без успеха между ними — письмом в личку через бота:
что за задача и что случилось. Один раз за серию: четвёртая и дальше
молчат, иначе больной чат завалил бы личку. Любой успех обнуляет серию.

- **Состояния нет.** Серия считается по журналу, поэтому рестарт ничего
  не теряет и не задваивает.
- **Частичные сбои не пишут.** «В три чата не ушло, а сто получили» — это
  журнал и карточка, а не письмо: иначе каждый круг слал бы письма.
- **Выключается галочкой.** «Писать о проблемах» — у каждой фоновой
  задачи; выключенные видно на карточке (🔕).
- **С кнопкой.** Письмо несёт «Открыть кабинет» — чинить в один тап.
- **Немая задача.** Сутки без доставок — письмо «молчит сутки» с тремя
  типовыми причинами. Тихий источник — тоже ответ, а не баг.

### Слушатель ключевых слов

Следит за чатом и присылает посты с вашими словами — с названием чата, без
учёта регистра. От уведомлений из диалогов отличается источником: те
слушают все ЛС аккаунта, а слушатель — один указанный чат.

- **Без слов не создаётся.** Слушатель без слов — это пересылка, а молча
  созданный «слушатель всего» завалил бы чат каждым постом. Правка тоже не
  даёт обнулить список.

### Парсер комментариев и инвайт

Третий режим парсера собирает комментаторов последних постов — самую
вовлечённую часть аудитории. У канала группа обсуждений находится сама, у
группы комментарии берутся из неё же. Лимит режет молчунов: сначала идут
самые разговорчивые.

- **Собранных можно позвать.** Поле «Звать в чат» + кнопка «Пригласить» в
  результатах: пачками по 20, кого позвать нельзя — помечается причиной и
  больше не трогается. FloodWait останавливает пачку, а не теряет её.
- **Выгрузка знает про комментарии.** Колонка «комментариев» появляется в
  CSV только когда они есть; остальным сборщикам формат не меняли.
- **Нет обсуждений — так и говорим.** Канал без группы обсуждений даёт
  понятную ошибку, а не пустой список и не падение.

### Клон канала с историей

Зеркало чужого канала: сначала забираются последние посты (до 500), дальше
новые выходят сами — живым путём пересылки, со всеми фильтрами, переводом
и кнопками. Новые посты не ждут конца догрузки.

- **Порциями по 20.** Залп в сотни постов — верный FloodWait; история идёт
  от старых к новым, как выходила. Прогресс — в заголовке задачи.
- **Пробок нет.** Удалённый или служебный пост считается обработанным:
  один такой пост иначе встал бы в очереди навсегда.
- **Пауза — своя на задачу.** Кого Telegram попросил подождать, тот и ждёт;
  повтор начинается с места остановки, а не с начала порции.

### Уникализация текста

Галочка у пересылки и веера — и чужой пост выходит «своим»: безопасные
синонимы («очень» → «весьма») плюс неотличимые на глаз буквы. Поиск не
опознаёт исходник, читатель не замечает разницы.

- **Детерминированная.** Один и тот же пост всегда даёт один и тот же
  текст: повторы не плодят разные версии.
- **Грамматику не калечит.** Меняются только слова из таблицы в известных
  формах; незнакомые формы трогаются лишь побуквенно.
- **Ложится последней.** Замены и подпись заданы обычными буквами — они
  применяются до подмены символов, иначе их паттерны не совпали бы.

### Автоперевод чужих постов

Код языка в настройках пересылки или веера (`ru`, `en`, `zh-CN`) — и каждый
пост из иноязычного источника выходит уже на языке читателя. Пустое поле —
честное «не переводить», мусор вместо кода отклоняется.

- **Переводится исходник.** Подпись и замены — уже на языке читателя, гонять
  их туда-обратно не надо. Фильтры смотрят исходник: они подбирают посты.
- **Не вышло — ушло как есть.** Переводчик недоступен — пост публикуется
  без перевода, а не теряется; пометка — в логе. Ретраи не делаем: каждая
  лишняя секунда — задержка поста у читателя.
- **Форвард не переводится.** Он несёт исходное сообщение целиком — там
  нечего переводить, и API не дёргается зря.

### Кнопки-ссылки под постами

Строки «текст | ссылка» в настройках задачи — и каждый пост выходит с
кнопками: подписка, магазин, чат. Не больше 6 под постом, текст — до 64
знаков, ссылка — http(s). Короткие `t.me/имя` дописываются сами.

- **Только в копии.** Форвард кнопок не умеет: слишком большое медиа уходит
  обычным форвардом без них — форма предупреждает, а не молчит.
- **Мусор — с номером строки.** Пустой текст, кривая ссылка, седьмая
  кнопка: задача не создаётся, а человек видит, какая строка виновата.
- **Работает везде, где копии**: пересылка канала, веер в несколько чатов,
  постинг и рассылка. В режиме «форвард» кнопки игнорируются.

### Закреп, ветка и часы жизни

У всех публикующих задач (пересылка, веер, постинг, рассылка, клон) — три
общие настройки: закреплять отправленное, слать в ветку (id топика группы)
и удалять пост через N часов (можно дробью: 0.5 — полчаса).

- **Ветка — только в режиме «копия».** Форвард чужого поста Telegram в
  топик не примет, поэтому задача с веткой в режиме «форвард» не
  создаётся: 400 с причиной, а не молчаливая потеря постов.
- **Часы жизни — порцией.** Посты удаляются тем же воркером, что шлёт:
  каждый проход забирает своё, гонки «удалить раньше отправки» нет.

### Упоминание всех

Галочка рассылки, постинга и веера: пост уходит с незаметными упоминаниями
первых 30 живых участников чата — без видимого текста, одними ссылками.
Боты пропускаются, недоступный состав — обычная отправка без упоминаний.
У веера состав собирается на каждый чат отдельно.

### Окно тишины и прогрев аккаунта

Окно «с–до» есть у всех отправляющих: вне окна задачи спят и продолжают
сами, когда время придёт. У пересылки окно работает через планировщик:
пост выходит с задержкой до утра, а не теряется.

- **Прогрев — по возрасту аккаунта**: свежие — до 50 отправок в сутки,
  дальше 150/400, зрелые — 1000. Рассылка и постинг при исчерпанном лимите
  встают до полуночи, пересылка и веер пропускают пост — с одной строкой
  в журнале на день.
- **Поверх прогрева — ручка**: «Отправок в сутки» у задачи перебивает
  прогрев в любую сторону. Разброс пауз и задержки (джиттер) убирает
  метроном: паузы плавают на случайные секунды.

### Постинг по датам

Галочка «Только по датам» превращает постинг из кругов по интервалу в
календарь: каждая дата — свой текст, наступила — ушла во все чаты. Окно и
интервал к датам не относятся. Не больше 50 дат на задачу.

- **Даты — местным временем.** Кабинет шлёт ISO с зоной устройства, сервер
  хранит UTC (`normalize_scheduled_posts`). Прошедшие даты разрешены: такой
  слот уходит на ближайшем проходе, а не теряется.
- **Прогресс — в слоте.** Кому уже ушло, пишется сразу: перезапуск посреди
  рассылки продолжает с того же чата, а не шлёт всё заново. Темп тот же,
  что у кругов: порция `POSTER_BATCH` за проход, пауза между чатами,
  FloodWait — паузой.
- **Мёртвый чат не держит слот.** Недоступный чат считается обработанным,
  причина — в журнале, слот закрывается.
- **Все даты ушли — задача встаёт на паузу**, как рассылка после заданных
  кругов. Новые даты заводятся правкой.
- **Правка не воскрешает ушедшее.** Состояние слотов сливается по id
  (`merge_scheduled_state`): отправленное остаётся отправленным.

### Парсер: режимы и фильтры

Состав чата — это все, включая мёртвые души; авторы сообщений — только те, кто
пишет. Поэтому у парсера два режима (`parser_mode`): «участники» листают состав,
«история» — авторов последних сообщений. В истории автор подтягивается отдельным
запросом: в сообщении есть только его id, а фильтрам нужны юзернейм и статус.

Фильтры (включены из коробки — «только с юзернеймом» и «не брать админов»,
остальное по желанию): Premium, аватарка, «только живые» (заходили в последние
трое суток) и «был в сети не раньше N часов назад». Админов парсер узнаёт одним
запросом — списком, а не проверкой каждого: иначе первый же большой чат упёрся
бы во FloodWait.

Два лимита вместо одного: «просмотреть» (`scan`) — сколько перебрать,
«сохранить» (`limit`) — сколько забрать. Фильтры отсеивают, и смотреть приходится
больше, чем забираешь. Сводка запуска говорит все три числа: собрано,
просмотрено, отсеяно фильтрами.

### Чаты выбираются мышкой

Поля «Источник» и «Чаты» в любой команде — не только ввод руками. Кнопка
«💬 выбрать» открывает список диалогов того аккаунта, который выбран в форме
(`GET /api/chats`, поиск по названию и `@username`), где чаты отмечаются пачкой,
а одиночное поле («Источник», «Приёмник» у копии канала) закрывает шторку сразу
по нажатию.
Выбранное подставляется как `@username` (числовой id — только если username
у чата нет), уже вписанное руками разбирается обратно в отметки, а отметка
рисуется на месте, без перерисовки списка: иначе на длинном списке прокрутка
отскакивала к первому чату после каждого нажатия.

Список бывает на сотни чатов, поэтому отмечать по одному не обязательно:

- строка «Выбрать все / Снять все» (`#pickerBulk`) действует на то, что
  **сейчас видно** — с поиском «Зеркало» отмечаются только зеркала, а не весь
  список. Рядом счётчик «отмечено N», на кнопке «Готово» — то же число;
- под полем стоит своя сводка (`#count_<key>`): «150 чатов @teatr_news,
  @afisha_demo и ещё 148» и ссылка «очистить». Без неё поле на 150 ссылок
  выглядело как каша, в которой не видно ни числа, ни ошибки.

### Лучшее время для постинга

Шторка постинга подсказывает окно по активности ленты за 14 дней
(`GET /api/activity/hours`): доставки журнала плюс пойманное ловцом —
то, когда лента живёт. Парсер не в счёт: его метки — время сбора.
Часы — в tz задачи, пик — лучшее двухчасовое окно, меньше десяти
событий — честное «пока мало данных». Окно ставится одной кнопкой.

### Массовые действия с задачами

У кого задач десятки, тот правит их пачками: «⏸ Все на паузу» на вкладке
активных, «▶ Все запустить» и «📦 Все в архив» — на стоящих
(`POST /api/tasks/bulk`). Область решает сервер: активные в архив пачкой
не уезжают, а рассылка с исчерпанными кругами после запуска начинает
круги заново — как в одиночном переключателе.

### Онбординг новичка

Бонусник без писем терялся: взял три дня за канал — и тишина. Теперь его
ведут три письма: день 0 — «подарок активен, создай первую задачу», день 1 —
«задач всё нет» (только если их правда нет), день 2 — «бонус кончается
завтра» (только неплатившим с живым сроком).

- **Своя цепочка.** Бонусники без оплат больше не получают общих писем
  платящим: «абонемент заканчивается» через минуту после подарка ушло.
- **Одно письмо за раз.** После простоя уходит старшее из созревших, а не
  вся пачка задним числом.

### Брошенная оплата

Счёт выставлен, деньги не пришли — через час письмо «вы не закончили
оплату» с кнопкой «Оплатить N ⭐»: она выставляет свежий счёт на тот же
срок. Разовые счета Stars (бот и кабинет) пишут висящую строку, зачёт её
закрывает — раньше следа не было вовсе, а оплаченные строки навсегда
оставались «pending» (попутно починено: теперь они paid).

- **Одно письмо.** Только про свежий счёт, только если с тех пор не платили
  другим, подарки и автопродление не дёргаем.
- **Старый счёт не мешает.** Оплата по нему закроет новый висящий: деньги
  есть деньги.

### Апсейл в упор

Бесплатно — 3 задачи, дальше стена. Стена теперь продаёт: называет потолок
и цену безлимита (N ⭐/мес), а кабинет вместо сухой ошибки и редиректа в
бота открывает пейволл с оплатой в один тап — инвойс звёзд поднимается
прямо из мини-аппа.

### Сводка владельца

«Статистика» в панели показывает деньги и воронку: выручка за 30 дней по
валютам, цепочка «подарков → платили (конверсия) → активны», новые за
неделю и кончившиеся абонементы. Оплата считается тем же предикатом, что
везде: статус paid либо старый след звёзд с чеком.

### Аналитика промокодов

Кнопка «Промокоды» в панели владельца: по каждому общему коду —
«активации → платящие», у скидочных — выручка с этим кодом. Зачёт помечает
платёж сработавшим кодом, коды на дни считают плативших после активации.
Личные коды (их десятки) идут одной сводной строкой.

### Цепочка конца и возврат ушедших

Конец срока теперь в четыре письма: «скоро конец» (за `RENEW_REMIND_DAYS`,
по умолчанию 3 дня) → «последний день» → «кончился» → через
`WINBACK_DAYS_AFTER` (по умолчанию 7 дней) возврат с личным промокодом
на −`WINBACK_PERCENT`% (по умолчанию 5). Возврат уходит только тем,
у кого стоят задачи и пустая копилка: замороженные дни — пауза, а не уход.
Ноль процентов выключает возврат: дёргать ушедшего без подарка — спам.
Продление снимает все метки цепочки.

### Подарочный абонемент

Месяц (в боте — любой срок) можно оплатить не себе, а другу: кнопка
«💝 Подарить абонемент» в меню оплаты и форма в кабинете. Друг должен быть
в базе — хотя бы раз запустить бота, — себе дарить нельзя. Платит даритель
звёздами (его скидка действует и на подарок), абонемент включается другу,
оба получают весть. Подарок — не оплата друга: награды пригласившему он
не даёт, автопродление в подарок не заворачивается.

### Скидка за друга

Друг за приход по ссылке получает личный одноразовый промокод на −5%
к первой оплате (размер — `REFERRAL_DISCOUNT_PERCENT`, 0 — без скидок),
пригласивший — такой же, когда друг оплатит первый абонемент. Код
вводится как обычный промокод — в боте или в кабинете, — а дешевле делает
ближайший разовый счёт любым способом: звёзды, карта, USDT. Гасится
скидка в момент зачёта платежа, неоплаченный счёт её не сжигает.
Автопродлению скидок нет: там Telegram списывает по первому счёту
каждый месяц, и разовая скидка стала бы вечной.

### Карточка задачи в боте

Бот показывает то же, что кабинет: запреты и лестницу мута у модератора,
полосу «ушло/всего» у постинга по датам, счёт вычищенных мёртвых чатов.
Список задач в кабинете встаёт каскадом — по очереди, а не все разом.

### Модерация чата

Чистильщик вырос в модератора: запретные слова и ссылки удаляются у всех
обычных участников, админы чата — вне подозрений. Рецидивист после N-го
нарушения уходит в мут на M часов; мут виден в журнале. Отдельный человек
по-прежнему вычищается точечно — прямое указание сильнее иммунитета.

## Как это работает технически

- **Бот-интерфейс** — aiogram 3: меню, FSM-диалоги, инвойсы Stars.
- **Чтение источников** — Telethon (личный аккаунт). Именно поэтому можно пересылать
  из чужих каналов: бот на Bot API так не умеет, а аккаунт — да.
- **Публикация** — тем же аккаунтом: скачиваем медиа и отправляем заново (`send_file`),
  либо обычным `forward_messages`, если выбран режим «форвард».
- **Хранение** — SQLAlchemy 2 (SQLite по умолчанию, PostgreSQL — одной строкой в `DATABASE_URL`).
  Схема обновляется сама: `ensure_schema()` добавляет недостающие колонки без потери данных.
  SQLite принудительно работает в **WAL** (`busy_timeout=10s`) — без этого на файловых
  системах с запрещённым `unlink` коммиты падают с `disk I/O error`.
- **Транзакции** — запись только через `session_scope()`: коммит при успехе, откат при
  исключении. Открывать `SessionLocal()` напрямую и писать без commit нельзя — при выходе
  из блока всё откатывается, и счётчики пересылок/журнал молча теряются. За этим следит
  тест `tests/test_persistence.py` (AST-проверка всего дерева `app/`).
- **Фон** — отдельные asyncio-задачи: обновление кэша правил (раз в минуту),
  проверка оплат (USDT через TronGrid, карта через ЮKassa) и напоминания
  о продлении — раз в 5 минут. Ссылку на задачу держим в модуле и отменяем
  на shutdown: без этого цикл писал в уже закрытую БД.
- **Мини-апп** — `app/webapp_api.py` раздаёт `webapp/` (чистый JS без сборки) и JSON-API.
  Авторизация — проверка подписи `initData` (HMAC-SHA256, TTL 24 часа). Вне Telegram
  кабинет открывается в демо-режиме на моках.
- **Ошибки** — единый контур `app/errors.py`: любые сбои API превращаются в JSON
  `{"error": "…"}` с корректным кодом (400/404/409/503/500), а исключения в хендлерах
  бота не оставляют пользователя с мёртвой кнопкой.
- **Логи** — loguru, уровень из `LOG_LEVEL` (TRACE…CRITICAL). Пишутся в stderr и
  в `logs/app.log` (ротация 10 МБ, хранение 14 дней). Конфигурируются **до** первого
  обращения к логгеру, поэтому падение на невалидном ключе видно сразу при старте.

### Очередь доставки

Входящее сообщение не уходит в Telegram сразу, а встаёт в очередь
(`app/telegram_client/queue.py`). Раньше каждое сообщение порождало отдельную
`asyncio.create_task` — сто постов, залетевших в канал разом, отправлялись
одновременно, скопом ловили FloodWait и терялись при перезапуске. Очередь
держит темп и границы:

| Что | Чем управляется | По умолчанию |
|---|---|---|
| Воркеры, разбирающие очередь | `DELIVERY_WORKERS` | 4 |
| Размер очереди (дальше — отброс) | `DELIVERY_QUEUE_MAXSIZE` | 2000 |
| Одновременных отправок на сервис | `SEND_GLOBAL_CONCURRENCY` | 8 |
| Минимальная пауза между отправками **одного аккаунта** | `SEND_MIN_INTERVAL_SECONDS` | 1.2 |
| Повторов при ошибке Telegram | `SEND_RETRY_ATTEMPTS` | 2 |
| База паузы между повторами | `SEND_RETRY_BASE_SECONDS` | 2.0 |
| Предел ожидания при FloodWait | `FLOOD_WAIT_MAX_SECONDS` | 900 |

Темп считается на каждый аккаунт отдельно — так же, как его считает сам
Telegram. Общая пауза на весь сервис замедляла бы одного пользователя из-за
активности другого: два аккаунта по одному сообщению ждали бы друг друга, хотя
лимита не нарушает ни один.

Как это выглядит на практике:

- **FloodWait** — ждём ровно сколько просит Telegram и повторяем. Если просят
  больше `FLOOD_WAIT_MAX_SECONDS`, не ждём: задача уходит в журнал ошибок.
- **Другие ошибки Telegram** (`RPCError`) — повтор с паузой 2 → 4 → 8 секунд.
- **Всё остальное** (БД, сеть, код) не повторяется: пять попыток упасть на
  одной и той же опечатке ничем не лучше одной.
- **Пауза держится вне слота отправки**, иначе правило, отдыхающее час по
  FloodWait, заблокировало бы остальные.
- **Задержка из правила** (`delay_seconds`) отрабатывается до постановки
  в очередь — правило с задержкой в час не занимает воркер.
- **Переполнение** — задача отбрасывается с записью в лог, а не растит память.

### Перезапуск не теряет отправки

Очередь живёт в памяти, поэтому раньше `systemctl restart` в неудачный момент
означал молча потерянные посты. Теперь задача сначала пишется в журнал ожидания
(`pending_deliveries`), и только потом уходит воркеру. Строка удаляется, когда
задача доведена до конца — отправлена, пропущена фильтром или окончательно
провалилась: иначе она повторялась бы после каждого перезапуска.

На старте сервис поднимает недоделанное (`restore_pending`): сообщение
перечитывается из источника по `message_id` — копию текста в БД не держим, там
могут быть личные переписки. Записи старше суток не восстанавливаются и
удаляются (`drop_stale_pending_deliveries`): в источнике такой пост уже
неактуален. За один раз поднимается не больше 500 отправок, чтобы после долгого
простоя в Telegram не улетела тысяча сообщений разом. Дважды одно и то же не
уйдёт: задача снимается с журнала по своему `delivery_id`.

### Сторож сервиса

Пассивный `/api/health` смотрит человек — когда вспомнит. Сторож пишет сам:
ошибок за пять минут больше `WATCH_ERRORS` (по умолчанию 20) — владельцу
летит «всплеск ошибок» с топом текстов; активных аккаунтов вне сети больше
`WATCH_OFFLINE` (по умолчанию 3) — «аккаунты не в сети». По каждому виду —
кулдаун `WATCH_COOLDOWN_MIN` (по умолчанию 60): часовая авария стоит одно
письмо. Нулевой порог вид выключает.

### Что видно в мониторинге

Состояние очереди отдаёт `GET /api/health` (без авторизации, для мониторинга):

```json
{"ok": true, "service": "tg-forward",
 "delivery": {"submitted": 12, "dropped": 0, "sent": 9, "failed": 0,
              "skipped": 3, "restored": 0, "queued": 0, "workers": 4,
              "pending_delays": 0, "persisted": 0,
              "skips": {"filtered": 2, "no_subscription": 1}}}
```

Пропуски идут с разбивкой по причинам, потому что лечатся они по-разному:

| Причина | Что значит |
|---|---|
| `filtered` | Не прошло фильтры правила — норма |
| `no_subscription` | У владельца правила кончился абонемент — это про деньги |
| `filter_error` | Сам фильтр упал: правило надо править |
| `service_message`, `empty_message` | Вступления, смена аватара, пустое сообщение |

Рост `queued` значит, что воркеры не справляются — пора поднимать
`DELIVERY_WORKERS` или `SEND_GLOBAL_CONCURRENCY`. Рост `failed` — смотреть
журнал пересылок в админке. Рост `persisted` при нулевом `queued` — задачи
записаны, но не разобраны: проверить, что очередь вообще поднялась.

При остановке сервиса очередь сначала дожимает то, что уже в работе
(`drain=True`, до 30 секунд), и только потом отключаются Telethon-клиенты —
иначе недоотправленное падало бы с ошибкой соединения.

## Быстрый старт локально

```bash
git clone <ваш-репозиторий> tg-forward && cd tg-forward
cp .env.example .env
```

Заполните в `.env`:

1. `BOT_TOKEN` — токен от [@BotFather](https://t.me/BotFather).
2. `API_ID` / `API_HASH` — [my.telegram.org](https://my.telegram.org) → API development tools.
3. `SECRET_KEY` — сгенерируйте: `python scripts/gen_secret.py`.
   **Потеря ключа = потеря всех сессий пользователей.**
4. `ADMIN_IDS` — ваш Telegram user_id (узнать: [@userinfobot](https://t.me/userinfobot)).

Запуск:

```bash
chmod +x run.sh deploy/deploy.sh
./run.sh          # создаст venv, поставит зависимости, запустит бота в long polling
```

Для локального запуска `WEBHOOK_URL` оставьте пустым — бот пойдёт на long polling.

Без `API_ID` / `API_HASH` приложение стартует, но вход аккаунтов отключён:
в логе будет `WARNING … бот и мини-апп стартуют, вход аккаунтов отключён`.
Всё остальное — меню, мини-апп, оплата — работает.

Ключи лучше иметь **свои**. Пары из открытого кода официальных клиентов
(самая частая — `api_id=2040` от Telegram Desktop) Telegram считает
опубликованными и на запрос кода для входа может ответить
`ApiIdPublishedFloodError`. Может и пустить: на этом сервисе вход по номеру
на паре `2040` проходил и аккаунт поднимался — то есть это риск, а не запрет.
Сервис узнаёт такие пары (`Settings.api_keys_are_public`) и предупреждает при
старте, а кабинет на отказе объясняет, что это ключи сервиса, а не проблема
номера. Менять пару на свою имеет смысл **до** первых подключений: сессия
привязана к `api_id`, под которым создавалась (см. ниже), и после подмены все
подключённые аккаунты придётся вводить заново.

### Подключить уже готовый аккаунт (без кода из Telegram)

Если аккаунт где-то уже авторизован и от него осталась «сырая» сессия —
`<auth_key в hex, 512 символов>:<номер DC>` или файл `*.session` от Telethon —
получать код повторно не нужно:

```bash
# из файла Telethon (точнее всего: DC, адрес и порт берутся из файла)
PYTHONPATH=. python scripts/import_session.py \
  --file ~/Downloads/255824769_telethon.session --save --user-id 7686196719

# только проверить ключ, ничего не записывая
PYTHONPATH=. python scripts/import_session.py --session "bd64...9131:1"

# проверить и записать в базу зашифрованной
PYTHONPATH=. python scripts/import_session.py --session "bd64...9131:1" \
  --save --user-id 7686196719
```

Скрипт разбирает три формата (`hex:dc`, `hex`, готовая StringSession), упаковывает
ключ в `StringSession`, подключается, печатает `get_me()` и кладёт сессию в БД
зашифрованной Fernet-ключом.

Если есть файл `*.session` (SQLite от Telethon), из него можно достать и `auth_key`,
и точные `dc_id`/`server_address`/`port`:

```bash
sqlite3 account.session "SELECT dc_id, server_address, port, hex(auth_key) FROM sessions"
```

**Важно:** `auth_key` привязан к `api_id`, под которым он создавался. Если сессия
сделана на официальных кредах Telegram Desktop (`2040`), а в `.env` стоит другой
`API_ID` — получите `AUTH_KEY_UNREGISTERED`, в худшем случае бан аккаунта.
Свои `API_ID`/`API_HASH` + вход по номеру в боте — единственный чистый путь;
официальные креды допустимы только как временная мера (нарушают ToS Telegram).

### Перенести аккаунт на другую машину (ноутбук → VDS)

Повторно входить по номеру не нужно: сессию можно вытащить из базы и
положить в базу на новом месте.

```bash
# на исходной машине: посмотреть, что есть, и выгрузить в файл
PYTHONPATH=. python scripts/export_session.py --list
PYTHONPATH=. python scripts/export_session.py --user-id 7686196719 --out /tmp/acc.session

# на новой машине (ключ там может быть другим — не страшно, сессия
# зашифруется заново уже местным SECRET_KEY)
RAW_SESSION=$(cat /tmp/acc.session) PYTHONPATH=. python scripts/import_session.py \
  --save --user-id 7686196719
```

Сессия в `--out`-файле создаётся с правами `600`; строка даёт полный доступ
к аккаунту, поэтому не коммитьте её и не пересылайте в чаты. После импорта
перезапустите сервис — в логе появится «Аккаунт #N на связи».

### Открыть мини-апп на локальной машине

Telegram открывает Web App только по HTTPS, поэтому нужен публичный адрес:

```bash
./scripts/expose.sh          # поднимает туннель, прописывает WEBAPP_URL в .env
./scripts/expose.sh --stop   # погасить
```

Скрипт сам находит `ngrok` или `cloudflared`, ждёт HTTPS-адрес, обновляет `WEBAPP_URL`
в `.env` и печатает напоминание перезапустить бота. После перезапуска в логе появится
«Кнопка мини-аппа установлена: …» — без этой строки кнопки не будет.

> Все бесплатные туннели показывают браузерам страницу-предупреждение
> («You are about to visit…»). Telegram WebView тоже её покажет — первый раз
> нужно тапнуть «Visit Site», дальше запоминается. В продакшене нужен свой
> домен и HTTPS, либо платный тариф туннеля.

Кабинет в обычном браузере: `http://127.0.0.1:8080/app/?demo=1` (демо-данные).

## Конфигурация

Все настройки — переменные окружения (`app/config.py`), список с комментариями —
в `.env.example`. При старте приложение делит проблемы на два типа:

**Фатальные** (`settings.require()`) — процесс не поднимается, в логе явная причина:

- нет `BOT_TOKEN` или `SECRET_KEY`;
- `SECRET_KEY` — не ключ Fernet (сгенерируйте: `python scripts/gen_secret.py`);
- задан `WEBHOOK_URL`, но пуст `WEBHOOK_SECRET` — вебхук без секрета принимает
  любое поддельное обновление.

**Мягкие** (`settings.warnings()`) — работа продолжается, в логе `WARNING`:

| Ситуация | Чем грозит |
|---|---|
| Нет `API_ID` / `API_HASH` | Вход аккаунтов отключён, остальное работает |
| `ADMIN_IDS` пуст | Админ-команды недоступны |
| Не задан `WEBAPP_URL` и `WEBHOOK_URL` | Кнопка мини-аппа у бота не появится |
| ЮKassa заполнена наполовину | Оплата картой молча не поднимется |
| `PAY_MODE=external`, но адрес страницы не собрать | Карта и USDT недоступны нигде |
| `PAY_MODE=inline` с картой или USDT | Продажа внутри Telegram не за Stars — риск по п. 6.2 |
| `EXTERNAL_PAYMENTS_URL` не на `https://` | Ссылка на оплату не откроется из Telegram |
| `DELIVERY_WORKERS` < 1 | Очередь доставки не сможет работать |
| `DELIVERY_QUEUE_MAXSIZE` < 10 | При всплеске посты начнут отбрасываться |
| `SEND_MIN_INTERVAL_SECONDS` < 0.5 | Высокий риск FloodWait |
| `BONUS_CHANNEL` не похож на публичный канал | Подарок за подписку отключён: проверять подписку нечем |
| Подарок за подписку включён | Напоминание: бот обязан быть администратором канала |

Значения очереди доставки поджимаются снизу (`max(1, …)`), поэтому кривое
значение не ломает запуск — но о намерении стоит напомнить.

«Половинчатые» значения не проходят молча: `mtproto_ready` отклоняет плейсхолдеры
вроде `0` или `your_api_id`, а не только пустые строки.

дней остался бы непройденным целиком.

## Деплой на VDS (24/7)

Требуется: Ubuntu/Debian, домен с HTTPS (для мини-аппа — Telegram WebApp
открывается только по HTTPS) и SSH-доступ.

Бот может работать двумя способами:

- **Long polling** (по умолчанию) — `WEBHOOK_URL` пуст. Не нужен публичный
  порт, проще всего. Работает сразу после заливки.
- **Webhook** — `WEBHOOK_URL=https://YOUR_DOMAIN`, путь `/webhook`. Экономит
  запросы, но требует, чтобы сервер был доступен по HTTPS извне.

Для мини-аппа HTTPS всё равно нужен — его отдаёт nginx поверх сервиса.

```bash
# 1. На сервере один раз: nginx + certbot
sudo apt update && sudo apt install -y nginx certbot python3-certbot-nginx

# 2. В .env на сервере:
#    HOST=127.0.0.1   PORT=8080
#    WEBHOOK_URL=            # пусто → long polling
#    WEBAPP_URL=https://YOUR_DOMAIN

# 3. Заливка кода (rsync + venv + systemd), см. deploy/deploy.sh
./deploy/deploy.sh root@YOUR_SERVER

# 4. Когда домен указывает на сервер (A-запись) — выпустить сертификат.
#    То же самое, но с проверками и понятным сообщением, если записи ещё нет:
scp deploy/https.sh root@YOUR_SERVER:/opt/tg-forward/deploy/
ssh root@YOUR_SERVER bash /opt/tg-forward/deploy/https.sh YOUR_DOMAIN

#    Вручную — certbot сам допишет блок 443 и HTTPS-редирект в конфиг nginx:
sudo certbot --nginx -d YOUR_DOMAIN
```

`deploy/https.sh` идёт по шагам и останавливается там, где что-то не готово:
сначала сверяет A-запись с IP сервера (и печатает, какую именно запись
добавить у регистратора), потом проверяет конфиг nginx, выпускает сертификат
и в конце проверяет, что `https://ДОМЕН/app/` отвечает 200. Скрипт можно
перезапускать — уже выпущенный сертификат он не перевыпустит, а только
проверит срок.

Конфиг nginx — в `deploy/nginx.conf`, systemd-юнит — в `deploy/tg-forward.service`.
Важно: nginx проксирует не только `/webhook`, но и `/` — иначе мини-апп (`/app/`)
и его API (`/api/`) снаружи недоступны, потому что приложение слушает только
`127.0.0.1:8080`.

До выпуска сертификата удобно отдавать сервис по HTTP (см. блок `listen 80`
в `deploy/nginx.conf`): так видно, что он жив, ещё без HTTPS. Как только
`certbot --nginx` выпустит сертификат, он добавит `listen 443` и редирект
`301 → https` — менять ничего вручную не нужно.

При первом деплое скрипт создаст на сервере `.env` из `.env.example` и остановится:
systemd читает этот файл через `EnvironmentFile`, а ключи у вас свои. Заполните
`.env` и запустите `./deploy/deploy.sh` снова.

```bash
systemctl status tg-forward     # статус
journalctl -u tg-forward -f     # логи в реальном времени
curl -s 127.0.0.1:8080/api/health   # счётчики очереди доставки
```

### Домен без покупки (nip.io) и ловушка 443

Если своего домена нет, для мини-аппа хватит бесплатного `*.nip.io` — он
указывает на нужный IP автоматически, A-запись не нужна:

```bash
# <IP сервера> меняется на ваш; имя перед ним — любое
ssh root@YOUR_SERVER bash /opt/tg-forward/deploy/https.sh \
   papa.107-173-89-192.nip.io
```

Но на VDS порт 443 часто уже занят — например, stream-блоком nginx с
`ssl_preread`, который разбирает входящий TLS по SNI и отдаёт VPN-бэкендам
(xray/VLESS). В этом случае HTTP-сайт на `listen 443 ssl` «не слышен»: запрос
с SNI нашего домена уходит на VPN и клиент видит чужой сертификат
(в логе — соединение, но сертификат не Let's Encrypt).

Признак на сервере:
```bash
echo | openssl s_client -connect 127.0.0.1:443 -servername YOUR_DOMAIN \
  | openssl x509 -noout -issuer   # должно быть "Let's Encrypt"
```

Лечится так: сайт слушает не 443, а отдельный порт (например `8443`), а в
карту SNI stream-блока добавляется строка, которая направляет наш SNI на
этот порт:
```bash
# /etc/nginx/stream-conf.d/*.conf, внутри `map $ssl_preread_server_name`:
YOUR_DOMAIN  127.0.0.1:8443;   # перед строкой default
```
и в `deploy/nginx.conf` меняем `listen 443 ssl;` → `listen 8443 ssl;`, затем
`nginx -t && systemctl reload nginx`. `deploy/https.sh --auto-sni` делает обе
правки сам (с бэкапами).

Теперь мини-апп открывается по `https://YOUR_DOMAIN` — стандартный 443, просто
трафик нужного SNI перенаправляется на 8443 внутри сервера.

### Проверить, что пересылка действительно работает

Самый быстрый способ — правило «из чата с ботом в Избранное»:

1. Отправьте боту `/start` с того аккаунта, который подключён как источник.
2. В мини-аппе создайте задачу «Копирование канала»: источник — `@ваш_бот`,
   приёмник — `me` (Избранное).
3. Напишите боту любое сообщение и подождите пару секунд.

```bash
# сообщение ушло — счётчик sent вырос
curl -s 127.0.0.1:8080/api/health | grep -o '"sent":[0-9]*'

# и в журнале появилась строка со статусом ok
sqlite3 data/app.db "SELECT id, rule_id, source_msg_id, target_msg_id, status
                     FROM forward_logs ORDER BY id DESC LIMIT 5"
```

Правило после проверки удалите. Если `sent` растёт, а сообщения не видно —
смотрите `failed` и `journalctl -u tg-forward`: причина (FloodWait, нет прав
писать в приёмник) остаётся в логе.

> ⚠️ Рекомендуется прокси для Telethon, если VDS за пределами РФ/СНГ:
> `PROXY=socks5://user:pass@host:port` в `.env`.

### Бэкапы базы

В `data/app.db` — зашифрованные сессии аккаунтов и платежи. Деплой ставит
таймер `tg-forward-backup.timer`: каждую ночь он снимает архив в `backups/`
(`BACKUP_DIR`, `BACKUP_KEEP` в `.env`) и удаляет старые сверх глубины.

```bash
python scripts/backup.py list                       # что есть
python scripts/backup.py backup                     # снять вручную
systemctl stop tg-forward                           # восстановить:
python scripts/backup.py restore backups/XXXX.tar.gz.enc --force
systemctl restart tg-forward
```

Два правила, без которых бэкапы — самообман:

1. **Задайте `BACKUP_PASSPHRASE`** — иначе архивы открытые, а внутри доступы.
   Пароль храните ВНЕ сервера (менеджер паролей, бумага): без него шифрованный
   архив не прочитать, а лежать он будет рядом с базой.
2. **Храните копию `SECRET_KEY` вне сервера.** Сессии в базе зашифрованы им:
   потеря ключа = потеря всех подключённых аккаунтов, бэкап не спасёт.

Postgres этим скриптом не накрывается — для него `pg_dump` по крону.

## Настройка оплаты

### Два контура: звёзды в Telegram, карта и крипта на сайте

Правила Telegram (ToS для разработчиков, п. 6.2) требуют продавать цифровые
товары внутри Telegram **только за Stars**. Поэтому способы оплаты разведены по
контурам, а выбирает контур `PAY_MODE`:

| `PAY_MODE` | Внутри бота и кабинета | На странице `/pay` |
|---|---|---|
| `external` (по умолчанию) | звёзды, заявка админу | карта/СБП, USDT |
| `stars` | звёзды, заявка админу | — (карта и USDT выключены) |
| `inline` | всё, как раньше | — |

Как это выглядит для человека: в боте и в кабинете есть кнопка
«🌐 Оплатить картой или криптой на сайте». Она открывает обычную веб-страницу
`https://<домен>/pay` — в кабинете через `WebApp.openLink`, то есть во внешнем
браузере, а не в WebView Telegram. Ничего не скрыто: на кнопке и в тексте прямо
написано, что оплата уходит на страницу сервиса.

Как это устроено:

- Ссылка подписана: `t=<user_id>.<months>.<expires>.<HMAC-SHA256(SECRET_KEY)>`,
  живёт час (`app/paylink.py`). Токен ничего не читает — он даёт право выставить
  счёт **на своего же** `user_id`, иначе `/pay?user=123` позволял бы выставлять
  счёта чужим людям. Кабинет просит свежий токен (`GET /api/pay/link`) в момент
  нажатия, а не при открытии.
- Счёт выставляет тот же код, что и в боте (`app/payments/service.py`): цену
  считает сервер по каталогу сроков, клиент передаёт только `months`. Больше
  пяти неоплаченных счетов одним способом сервис не выставит.
- Доступ включается сам: фоновый цикл раз в 5 минут спрашивает у ЮKassa и
  TronGrid статус висящих счетов и присылает подтверждение в бот. Кнопки
  «Я оплатил» на странице нет — она там и не нужна.
- Брошенные счёта закрываются: карта — через 24 часа, USDT — через 72
  (`repo.expire_stale_payments`). Иначе метка-сумма USDT остаётся занятой
  навсегда, а лимит висящих счетов запирает человека без нового счёта.

`EXTERNAL_PAYMENTS_URL` нужен, только если страница живёт на другом домене;
по умолчанию адрес строится из `WEBAPP_URL`/`WEBHOOK_URL` + `/pay`. При
`PAY_MODE=inline` с настроенной картой или USDT сервис на старте пишет в лог
предупреждение о п. 6.2 — режим оставлен, но риск блокировки на вас.

> Контур снижает риск, но не убирает его совсем: Telegram смотрит и на то, что
> бот рекламирует. Оплата на стороннем сайте — обычная практика (так работают
> подписки многих сервисов), но окончательное решение всегда за платформой.

### Telegram Stars — самый быстрый старт
Ничего подключать не нужно, работает сразу. Цена — `PRICE_STARS`.
Вывод средств: через [@xRocket](https://t.me/xrocket) или Fragment.

Срок выбирается из каталога — **1, 3, 6 или 12 месяцев** (`app/plans.py`).
Он один и для бота, и для кабинета: цена считается умножением
`PRICE_STARS × months` на сервере, поэтому кнопки не расходятся со счётом.
Добавить срок — значит добавить его в `PERIODS`, и он появится в обоих местах.

Оплата из кабинета идёт не покидая мини-апп:

1. Мини-апп дёргает `POST /api/subscription/invoice` (срок — 1…12 месяцев).
2. Бэкенд сам считает сумму (`PRICE_STARS × months`) и создаёт инвойс через
   Bot API `createInvoiceLink`. Клиент передаёт только срок, не цену.
3. Мини-апп открывает ссылку через `WebApp.openInvoice`, зачисление приходит
   в хендлер `successful_payment` бота — второй реализации оплаты нет.

Вне Telegram (обычный браузер, демо-режим) `openInvoice` недоступен — кнопка
честно уводит в диалог с ботом, а не делает вид, что платёж начался.
Если Bot API недоступен, вместо 500 приходит 503 с `status: invoice_failed`.

### Автопродление за Stars
Кнопка «🔁 Автопродление» (в выборе срока и в кабинете) выставляет не разовый
счёт, а подписку: Telegram списывает месяц сам каждые 30 дней, а продлевает его
тот же хендлер `successful_payment`. Ничего настраивать не нужно.

- Включённое продление видно строкой в карточке абонемента и в кабинете.
- Отмена — в настройках Telegram (Stars → Подписки): Bot API об отмене боту
  не сообщает, поэтому флаг снимается, когда срок истёк без списания.
- Рекуррентные списания подтверждаются своим текстом — «Автопродление
  сработало», а защита от повторных апдейтов та же, что у разовых счетов.

### ЮKassa (карты, СБП)
Нужна самозанятость/ИП + договор с [ЮKassa](https://yookassa.ru). Заполните в `.env`:
`YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_RETURN_URL`.
При `PAY_MODE=external` (по умолчанию) карта работает на странице `/pay`,
а доступ включает фоновая проверка статуса платежа.

### USDT (TRC-20)
Укажите `USDT_TRC20_WALLET` и, желательно, `TRONGRID_API_KEY`.
Каждому платежу выдаётся **уникальная сумма** (например `12.017` вместо `12.00`) —
по ней сервис сам находит перевод и включает доступ.

### Вручную
Кнопка «Через администратора» шлёт заявку вам в личку, вы выдаёте доступ командой
`/grant <user_id> <месяцев>`.

## Копилка подписок

Дни абонемента не сгорают: их можно заморозить (`POST /api/subscription/bank`)
и позже вернуть (`POST /api/subscription/distribute`), в том числе распределив
между своими аккаунтами. Всегда остаётся минимум сутки активного периода,
поэтому заморозить «всё и сразу» нельзя.

## Бесплатные дни за подписку на канал

Разовый подарок: человек подписывается на канал сервиса и получает дни работы
задач. Включается двумя переменными:

```env
BONUS_CHANNEL=@papin4_do4a   # пусто — подарка нет вовсе
BONUS_DAYS=3                 # 0 — тоже выключатель
```

Канал в `.env` можно писать как удобно — `@имя`, `имя`, `https://t.me/имя`,
`t.me/имя` или числовой `-100…`: Bot API получит один и тот же вид. Приватная
ссылка-приглашение (`t.me/+хеш`) не годится — по ней подписку не проверить, и
сервис скажет об этом предупреждением на старте.

> **Бот обязан быть администратором этого канала.** Иначе `getChatMember` не видит
> подписчиков, и любая проверка честно отвечает «не смогли проверить, попробуйте
> позже» — а не «вы не подписаны». Об этом же напоминает предупреждение на старте.

Как это выглядит для человека: в меню оплаты первой строкой «🎁 3 дн. за подписку
на канал» (самый дешёвый путь — сверху), дальше карточка с кнопками «Открыть
канал» и «Проверить подписку». В кабинете то же самое отдельной карточкой.
После начисления кнопка проверки исчезает — второй раз дарить нечего.

Правила, которые держит сервер (`app/bonus.py` — один и тот же код для бота и
кабинета):

- **Ровно один раз на аккаунт.** Начисление идёт условным `UPDATE … WHERE
  channel_bonus_at IS NULL`, поэтому ни второе нажатие, ни два одновременных
  запроса второго подарка не дают. Отписаться и подписаться заново тоже не помогает.
- **Дни складываются, а не заменяют.** Активный абонемент продлевается на N дней,
  истёкший начинается заново от «сейчас» — иначе подарок достался бы прошлому.
- **Отказ не оставляет следов.** Если дни не начислены, метка «подарок выдан» не
  ставится: транзакция откатывается целиком.
- **«Не подписан» и «не смогли проверить» — разные ответы.** Во втором случае
  виноваты мы (бот не администратор, Telegram недоступен), и звать подписаться
  заново нельзя.

`POST /api/subscription/bonus` (подпись Telegram обязательна) отвечает разными
кодами — кабинет по ним понимает, что делать:

| Код | `status` | Что значит |
|---|---|---|
| 200 | `granted` | Дни начислены, в теле `days` и `until` |
| 403 | `not_member` | Не подписан — кабинет открывает канал через `openTelegramLink` |
| 409 | `already` | Подарок уже получен ранее |
| 503 | `unavailable` | Не смогли спросить Telegram (чаще всего бот не админ канала) |
| 503 | `disabled` | Подарок не настроен |

Состояние подарка видно и в `/api/me` — блок `bonus` с полями `enabled`,
`channel`, `url`, `days`, `claimed`, `claimed_at`. Повторный запрос к Telegram при
уже полученном подарке не делается: ответ приходит сразу из базы.

## Бонусная политика

Все бонусы в сервисе — скромные осознанно: большой лёгкий бонус тут же
начинают фармить, а маленький честно работает годами. Стандарт один:

- **дни — 3**: подарок за подписку на канал (`/bonus`) и награда
  пригласившему за оплатившего друга;
- **скидки — 5%**: реферальные коды другу и пригласившему, письмо возврата
  ушедшим. Срабатывают только на реальные деньги, поэтому фармить их
  бессмысленно: без оплаты скидка — просто строка.

Исключения — только явные решения владельца: промокоды `/promo_new`
(дни и проценты на его усмотрение), ручная выдача `/grant`, подарок
абонемента (покупатель платит полную цену). Пробный период выключен
(`TRIAL_DAYS=0`): бесплатный вход — только через подписку на канал.

## Реферальная программа

Друг приходит по ссылке — ему скидка, оплачивает первый абонемент —
пригласившему дни. Включается тремя переменными:

```env
REFERRAL_DAYS=3              # дней за платящего друга; 0 — программа выключена
WATCH_ERRORS=20             # ошибок за 5 мин — письмо владельцу; 0 — выкл
WATCH_OFFLINE=3             # аккаунтов вне сети — письмо; 0 — выкл
REFERRAL_DISCOUNT_PERCENT=5  # скидка обоим; 0 — без скидок
BOT_USERNAME=                # юзернейм бота без @ — для ссылки t.me/<имя>?start=ref_<id>
```

Ссылка живёт на экране /ref, кнопкой в меню абонемента и карточкой в
кабинете. Правила, которые держит сервер (`app/referral.py`):

- **Дней за регистрацию нет.** Их фармили пачками фейков, и они ломали
  правило «бесплатно — только за подписку на канал». Друг за приход получает
  только промокод на скидку к первой оплате.
- **Награда — за первый платёж.** Пригласившему дни и код начисляются, когда
  друг оплатит первый абонемент (звёзды, карта, USDT; ручная выдача админа
  не считается). Один друг — одна награда, флаг взводится условным `UPDATE`,
  второй платёж того же друга ничего не даёт. Бонус скромный осознанно.
- **Фарм убыточен.** Чтобы получить награду, надо сначала заплатить за месяц:
  гонять фейков ради дней дороже, чем сами дни.
- **Дарят приход новичка, а не открытие ссылки.** Аккаунт старше десяти
  минут по чужой ссылке не привязывается.
- **Себе нельзя.** Своя ссылка себе не начисляет.
- **Пригласивший — первый и навсегда.** Вторая ссылка не перепривязывает,
  привязка ставится условным `UPDATE … WHERE referred_by IS NULL`, поэтому
  два одновременных захода дают одну выдачу.
- **Вести сразу.** Пригласившему уходит сообщение и о приходе друга, и о
  награде за его первый абонемент, — ждать и проверять не нужно.

## Промокоды

Акции вида «код на выходных»: владелец создаёт код, люди вводят его в боте
или в кабинете и получают дни. Создаётся командой:

```
/promo_new LETO 7 100 3   — код LETO на 7 дней, первым ста, живёт 3 дня
/promo_new SALE 20% 500 3 — код SALE на −20% к оплате, первым пятистам, живёт 3 дня
```

Код на скидку вместо дней встаёт в ожидание и дешевле делает ближайший
разовый счёт (звёзды, карта, USDT) — механика одна с реферальными скидками.
Лимит — сколько человек успеют активировать (без него — все), срок —
сколько дней код живёт (без него — бессрочно). Вводят код командой
`/promo КОД`, кнопкой «Ввести промокод» в меню абонемента или полем в
кабинете. Правила, которые держит сервер (`app/promocode.py`):

- **Один код — один раз на человека.** Повторная активация тем же
  человеком запрещена схемой (`UNIQUE(code_id, user_id)`), а не проверкой
  «если», — гонку двух одновременных запросов держит база.
- **Лимит не переполняется.** Счётчик растёт условным `UPDATE … WHERE
  used_count < max_uses`: два запроса на последний слот дают одну выдачу.
- **Ввод как угодно.** Код нормализуется (верхний регистр, без пробелов):
  « лето » и «ЛЕТО» — один код.
- **Выключенный код — как несуществующий.** Перебору подсказывать нечего.

## Проверка перед запуском и статусы задач

При создании задачи кабинет сначала показывает найденные чаты, окно отправки,
паузы, даты публикаций и до пяти примеров собственных текстов после преобразований.
Запрос `POST /api/tasks?preview=1` проходит те же проверки, что и создание,
но не сохраняет задачу или сообщения в библиотеку и не запускает отправку.
Отмена возвращает в форму; кнопка «Запустить» создаёт задачу отдельным запросом.
Перевод, медиа и случайные варианты явно отмечены как ограничения предпросмотра.

Карточки показывают ограничение аккаунта с датой окончания паузы, отсутствие
связи, удалённые сообщения библиотеки, ожидание окна и ближайшую дату публикации.
Расписание по конкретным датам не зависит от общего окна отправки.

Проверки: `python -m pytest tests/test_task_preview.py` и
`node tests/task_preview_ui.cjs` (статусы, отмена и подтверждение запуска).

## Интерфейс мини-аппа

Кабинет — `webapp/` (HTML + CSS + JS, сборка не нужна). Лицо сервиса — знак
**ДОЧА**: корона в шапке, на экране загрузки, в герой-блоке «Главной», в центре
навигации и в состоянии ошибки. Один и тот же SVG-символ `<symbol id="crown">`,
подключаемый через `<use>` — правится в одном месте.

Что есть в интерфейсе:

- **Состояния загрузки** — скелетоны вместо пустого экрана; показываются только
  при первой загрузке списка, поэтому переключение вкладок не мигает.
- **Состояния ошибок** — вместо «ничего не найдено» блок с короной, текстом причины
  и кнопкой «Повторить» (`data-retry` слушается делегированием).
- **Занятые кнопки** — `withLoading()` крутит спиннер и блокирует повторный тап,
  метка кнопки сохраняется.
- **Каталог читается сразу** — карточки разложены по пяти блокам, над списком ряд
  чипсов-фильтров («все 10», дальше блоки со своими числами), а в подвале
  карточки — метки отличий. Всё это приходит с сервера (`commands_payload`), в
  `webapp/app.js` лежит только демо-копия для прогона без Telegram; старый
  сервер без `tags` рисуется как раньше.
- **Сколько уйдёт сообщений видно в форме** — под полем «Сообщение» счётчик и
  заголовок первого сообщения (`renderMessageCount`), делит их пустая строка
  ровно так же, как на сервере. То же под полем библиотеки (`#libraryDraft`).
- **Выбор мышкой** — одна шторка (`#pickerSheet`) в двух режимах: чаты для полей
  формы и сообщения из библиотеки. Список с поиском и отметками у них общий —
  два почти одинаковых экрана разошлись бы при первой же правке. Для списков
  на сотни чатов сверху строка «Выбрать все / Снять все» по видимому, снизу
  «Готово · N», а под самим полем — сводка выбранного с ссылкой «очистить».
- **Адаптивность** — колонка центрируется на широких экранах, а кнопки переносятся
  всегда, а не по медиазапросу: обычный экран в Telegram — 390 px, и это не «узкий
  случай». Ряд подписки — сетка `1fr 1fr` с оплатой звёздами во всю ширину, ряд
  действий задачи переносится сам, корзина держит свой столбец.
- **Свежесть после выката** — ссылки на `styles.css` и `app.js` (и адрес самого
  кабинета в кнопках бота) содержат `?v=<метка сборки>`; метка считается по
  содержимому файлов (`app/webapp_build.py`). Без этого Telegram WebView отдаёт
  вёрстку из своего кэша, и деплой «не виден»: HTML уходит с `Cache-Control:
  no-store`, статика без метки — с `no-cache`, а с меткой — `immutable`.
- **Кабинет обновляется сам** — метка есть и в `/api/health`; на старте кабинет
  сверяет её с той, что в своём адресе, и при расхождении перезагружается на
  адрес с новой (`reloadIfBuildIsStale` в `webapp/app.js`). А `app.js` без метки
  запрашивает только старая копия `index.html`, застрявшая в кэше клиента: ей
  вместо бандла отдаётся скрипт-спасатель, который уводит на адрес с меткой
  вместе с `location.hash` (в нём initData). Так старый кабинет из кэша чинится
  без «почистите кэш» и без переустановки Telegram.
- **Доступность** — контраст текста к фону не ниже 5.6:1 (`--muted` — 7.45:1, AAA),
  видимый фокус на всех интерактивных элементах (для срезанных `clip-path` углов —
  внутренняя рамка через `box-shadow: inset`, внешний `outline` бы обрезался),
  `prefers-reduced-motion` полностью выключает анимации.
- **Производительность** — анимируются только `transform` и `opacity`, шиммер
  скелетонов сделан на `translateX`, а не на `background-position`.
- **Оплата звёздами** — кнопка сама показывает цену (`⭐ Оплатить 299 звёзд`,
  сумма приходит в `/api/me` вместе с тарифами) и открывает инвойс поверх
  кабинета: `paid`/`pending`/`failed` — тост, `cancelled` — молчим.
- **Оплата на сайте** — отдельная кнопка «🌐 Оплатить картой или криптой на
  сайте» появляется только если контур включён (`pay.external` в `/api/me`).
  Открывает страницу `/pay` через `WebApp.openLink` — во внешнем браузере,
  не в WebView Telegram.
- **Подарок за подписку** — карточка на «Подписке» вместо прежней заглушки:
  сколько дней дарим, кнопка «Открыть канал» (именно `openTelegramLink`, иначе
  внешний браузер покажет страницу, где человек не подписан) и «Проверить
  подписку». После начисления карточка переходит в «уже получено», а бейдж дней
  растёт сразу. Отказ 403 сам открывает канал — подписываться и проверять
  приходится не в два обратных шага.

> **Уточнение про «мини-карту».** Никакой карты в проекте нет: ближайшее совпадение
> в коде — кнопка «💳 Карта / СБП» (это способ оплаты) и вызовы `Array.map()`.
> Анимацию загрузки добавил туда, где она действительно нужна, — в мини-апп:
> скелетоны списков и экран загрузки с Папой.

## Юридические и технические нюансы

- Сервис работает через личные аккаунты пользователей — это разрешено Telegram, но
  **злоупотреблять нельзя**: ставьте задержки, не делайте тысяч пересылок в час,
  иначе аккаунт ловит `FloodWait` или ограничения.
- Цифровые товары внутри Telegram продаются только за Stars (ToS для
  разработчиков, п. 6.2). Поэтому по умолчанию (`PAY_MODE=external`) карта и
  крипта живут на странице сервиса вне Telegram, а внутри бота остаются звёзды.
  Это снижает риск, но не отменяет его: смотрят и на то, что бот рекламирует.
- Альбомы (несколько фото одним постом) приходят как отдельные сообщения —
  они пересылаются по одному. Это стандартное поведение и для коммерческих аналогов.
- Медиа больше 50 МБ не скачивается для «чистой» пересылки — уходит обычным форвардом.
- Сессии шифруются Fernet-ключом. Держите `SECRET_KEY` в секрете и в бэкапе.
  Им же подписываются ссылки на оплату (`app/paylink.py`): смена ключа
  обесценивает выданные ссылки — это нормально, они живут час.

### Полезные мелочи

- `utils.smart_edit()` — правка сообщения с учётом медиа: если у сообщения есть
  фото, правится `caption`, иначе `text`. Без этого все кнопки меню молча
  перестают работать после `/start` с баннером (Telegram: «there is no text in
  the message to edit»).
- Если `assets/welcome.jpg` нет, `/start` отправляет текстовое приветствие —
  баннер необязателен.

### Профиль аккаунта и очередь вступлений

В разделе «Аккаунты» доступны кнопки «Профиль», «Вступить в чаты» и «Диагностика».
Профиль загружается из Telegram. Имя, фамилия, описание (до 70 символов), дата рождения
(год необязателен) и основное фото меняются только после подтверждения пользователя.
Фото: JPEG/PNG до 512 КБ, 160–4096 пикселей. Частичный успех нескольких операций
показывается явно; после ошибки нужно заново открыть профиль и проверить результат.
Профиль и дата рождения не сохраняются в базе сервиса.

Автоподписка из кабинета запускается в фоне. Карточка показывает текущий чат и
сохранённые результаты: вступление, уже участник, заявка отправлена или ошибка.
Кнопка «Остановить» прерывает очередь; повторный запуск пропускает подтверждённые
вступления и отправленные заявки. После перезапуска сервиса продолжение ручное.
Отключение аккаунта, пауза/архивирование/удаление задачи тоже останавливают очередь.
FloodWait останавливает обработку без автоматических повторов и сохраняет срок
ожидания, в том числе для других задач аккаунта. PeerFlood включает защитную паузу.
Дневные ограничения сервиса сохраняются. Заполнение профиля и выбранная задержка
не гарантируют отсутствие ограничений Telegram.

Диагностика объединяет связь с аккаунтом, защитную паузу сервиса, последние ошибки
задач и результаты вступлений. Срок защитной паузы не является обещанием Telegram
снять спамблок; статус можно самостоятельно уточнить через ссылку на @SpamBot.

Проверки: `python -m pytest -q tests/test_account_profile.py tests/test_join_queue.py`
и `node tests/task_preview_ui.cjs`.
